Executor foundations

KEY TOPICS

  • Executor foundations: essential API behaviour, implementation choices, and common interview trade-offs.
  • Focus on lifecycle, concurrency correctness, failure handling, and practical code design.

Q1. What problem does the Executor framework solve?

Answer: It separates task submission from the mechanics of creating, scheduling, and managing threads. Callers submit Runnable or Callable tasks; an Executor decides how they run.

Q2. What is the difference between Executor and ExecutorService?

Answer: Executor exposes execute(Runnable). ExecutorService adds lifecycle management, submit methods, Future results, bulk execution, and termination control.

Q3. How do you execute a task with the simplest Executor?

Answer: Create an Executor and call execute. The implementation decides which thread runs the task.

Q4. What is the difference between execute() and submit()?

Answer: execute accepts Runnable and returns void; uncaught task failures reach the worker's uncaught-exception handling. submit returns a Future and captures task failure for get() to report as ExecutionException.

Q5. Why should applications reuse a thread pool?

Answer: Thread creation has cost. A pool reuses workers, bounds concurrency when configured appropriately, and centralizes lifecycle and queueing.

Executor foundations · continued

Q6. What does Executors.newFixedThreadPool(n) create?

Answer: A pool with up to n active workers and an unbounded shared queue. It limits active threads but not queued work, so sustained overload can consume memory.

Q7. What does newCachedThreadPool() do?

Answer: It creates workers as needed and reuses idle workers; it can grow to a very large number of threads under bursts. Use cautiously for unbounded or blocking workloads.

Q8. What does newSingleThreadExecutor() guarantee?

Answer: Tasks execute sequentially using one worker, preserving submission order for tasks in its queue. If the worker dies, another is created to continue.

Q9. What is a work queue in ThreadPoolExecutor?

Answer: It holds submitted tasks waiting for a worker. Queue choice affects latency, throughput, memory use, and whether the pool grows.

Q10. When should you prefer an explicit ThreadPoolExecutor?

Answer: When you need control over core/max sizes, keep-alive, queue capacity, thread factory, rejection policy, metrics, or dynamic tuning.

Q11. How do you submit a Runnable?

Answer: Use executor.submit(runnable) to receive a Future<?> or executor.execute(runnable) when no result is needed.

Q12. How does Callable differ from Runnable?

Answer: Callable<V>.call() returns V and may throw checked exceptions. Runnable.run() returns void and cannot declare checked exceptions.

Q13. Write a Callable that returns a value.

Answer: Example: Callable<Integer> task = () -> 40 + 2; Future<Integer> f = pool.submit(task); int answer = f.get();

Q14. How do you pass data into a task?

Answer: Capture effectively-final local variables in a lambda, or pass an immutable task object with constructor arguments. Avoid unsafely sharing mutable state.

Q15. How do you return multiple values from a Callable?

Answer: Return a small immutable record or DTO, for example record Result(int count, String status) {}.

↑ Contents6

Runnable and Callable coding · continued

Q16. Can a Callable be submitted to execute()?

Answer: No. execute accepts Runnable. Use submit(Callable) or adapt a Callable with a FutureTask, which implements RunnableFuture.

Q17. How do you adapt Callable to Runnable?

Answer: FutureTask<Integer> ft = new FutureTask<>(callable); pool.execute(ft); Integer value = ft.get();

Q18. How do you submit a task and ignore its result?

Answer: pool.submit(() -> performWork()); Keep the Future if cancellation or error observation matters; otherwise execute may be clearer.

Q19. How do you handle checked exceptions inside Runnable?

Answer: Catch and handle them inside run(), or wrap them in an unchecked exception. With submit, inspect Future.get() to observe captured failures.

Q20. What happens if a submitted Callable throws?

Answer: The Future completes exceptionally. Calling get() throws ExecutionException whose cause is the original exception.

Future and cancellation

KEY TOPICS

  • Future and cancellation: essential API behaviour, implementation choices, and common interview trade-offs.

Q21. What does Future represent?

Answer: A handle to an asynchronous computation. It supports completion checks, blocking result retrieval, and cancellation attempts.

Q22. How do you retrieve a Future result?

Answer: Call future.get(); it blocks until completion and may throw InterruptedException or ExecutionException.

Q23. How do you avoid waiting forever on get()?

Answer: Use future.get(timeout, unit). It throws TimeoutException if the result is not ready by the deadline.

Q24. What is the difference between isDone() and isCancelled()?

Answer: isDone is true for normal completion, exceptional completion, or cancellation. isCancelled is true only when cancellation succeeded.

Q25. How do you cancel a running task?

Answer: Call future.cancel(true) to request interruption, or cancel(false) to avoid interrupting a running worker. The task must cooperate with interruption.

↑ Contents8

Future and cancellation · continued

Q26. Does cancel(true) forcibly stop a thread?

Answer: No. It requests interruption; Java does not safely force-stop arbitrary code. Tasks must check interruption or use interruptible operations.

Q27. How should a task respond to interruption?

Answer: Propagate InterruptedException where possible. If it cannot be propagated, restore the flag with Thread.currentThread().interrupt() and exit or clean up.

Q28. What is the difference between get() and join()?

Answer: Future.get reports failure using checked ExecutionException and interruption. CompletableFuture.join reports failure using unchecked CompletionException and does not declare InterruptedException.

Q29. How can you collect results from several Futures?

Answer: Keep a list of Future<T>, submit all tasks, then call get() on each. For completion-order processing, use ExecutorCompletionService.

Q30. What is ExecutorCompletionService?

Answer: It wraps an Executor and places completed tasks on a completion queue, allowing consumers to retrieve results as tasks finish rather than submission order.

ThreadPoolExecutor internals

Q31. Explain corePoolSize and maximumPoolSize.

Answer: The pool first creates workers up to corePoolSize. Once core workers are busy, it queues tasks; if the queue cannot accept more, it may grow toward maximumPoolSize.

Q32. What is keepAliveTime?

Answer: The idle time after which excess workers beyond the core size may be terminated. Core-thread timeout can also be enabled.

Q33. What happens with an unbounded queue?

Answer: After core workers are busy, tasks normally queue indefinitely, so maximumPoolSize generally has no practical effect and queue growth can be unbounded.

Q34. Why use a bounded queue?

Answer: It places a limit on waiting work and enables backpressure through rejection handling instead of allowing memory growth without bound.

Q35. What is SynchronousQueue?

Answer: A zero-capacity handoff queue: a submitted task must be handed directly to a worker. It is useful when direct handoff and pool growth are desired.

↑ Contents10

ThreadPoolExecutor internals · continued

Q36. What is ArrayBlockingQueue?

Answer: A bounded FIFO array queue with fixed capacity. It offers predictable memory use but requires choosing a capacity.

Q37. What is LinkedBlockingQueue?

Answer: A linked FIFO queue that may be bounded or effectively unbounded. Specify a capacity when overload must be contained.

Q38. What does allowCoreThreadTimeOut(true) do?

Answer: It allows core workers to terminate after keepAliveTime when idle, useful for pools that should shrink to zero or reduce idle resource use.

Q39. How can you prestart core threads?

Answer: Call prestartCoreThread() for one worker or prestartAllCoreThreads() for all core workers, avoiding startup latency on initial submissions.

Q40. How do you inspect pool health?

Answer: Use getPoolSize(), getActiveCount(), getTaskCount(), getCompletedTaskCount(), getQueue().size(), and rejection/latency metrics. Treat estimates as monitoring signals, not synchronization.

Rejection and backpressure

KEY TOPICS

  • Rejection and backpressure: essential API behaviour, implementation choices, and common interview trade-offs.
  • Focus on lifecycle, concurrency correctness, failure handling, and practical code design.

Q41. When is a task rejected?

Answer: When shutdown has begun or the executor cannot accept work under its queue and worker limits.

Q42. What does AbortPolicy do?

Answer: It throws RejectedExecutionException to the submitting thread. This makes overload explicit and is a useful default for controlled failure.

Q43. What does CallerRunsPolicy do?

Answer: It runs the rejected task on the submitting thread, slowing producers and creating a simple feedback-based backpressure mechanism.

Q44. What does DiscardPolicy do?

Answer: It silently drops the rejected task. Use only when losing that work is explicitly acceptable and observable by design.

Q45. What does DiscardOldestPolicy do?

Answer: It removes the queue head and retries submission. It can lose older work and should be used only when that trade-off is valid.

↑ Contents12

Rejection and backpressure · continued

Q46. How would you implement a rejection counter?

Answer: Implement RejectedExecutionHandler; increment a thread-safe counter and then throw, run, or route the task according to an explicit policy.

Q47. How do you prevent overload from exhausting memory?

Answer: Bound the queue, cap maximum threads, reject or throttle producers, set request deadlines, and monitor queue depth and task age.

Q48. What is backpressure in a thread pool?

Answer: A mechanism that makes producers slow down or fail when consumers cannot keep up, rather than accumulating unlimited pending tasks.

Q49. Why can CallerRunsPolicy be dangerous in web request threads?

Answer: A request thread may unexpectedly perform slow background work, increasing request latency and consuming server request capacity.

Q50. How should critical tasks be handled during rejection?

Answer: Define durable retry or handoff semantics, idempotency, and alerting. Do not silently discard tasks whose completion is required.

Shutdown and lifecycle

KEY TOPICS

  • Shutdown and lifecycle: essential API behaviour, implementation choices, and common interview trade-offs.
  • Focus on lifecycle, concurrency correctness, failure handling, and practical code design.

Q51. What does shutdown() do?

Answer: It stops accepting new tasks while allowing previously submitted tasks to finish. It does not wait for termination.

Q52. What does shutdownNow() do?

Answer: It attempts to interrupt active workers and returns tasks that never commenced. It is best-effort, not a guaranteed stop.

Q53. How do you wait for graceful termination?

Answer: Call shutdown(), then awaitTermination(timeout, unit). If it times out, call shutdownNow() and await again.

Q54. Write a standard two-phase shutdown pattern.

Answer: pool.shutdown(); try { if (!pool.awaitTermination(30, SECONDS)) { pool.shutdownNow(); } } catch (InterruptedException e) { pool.shutdownNow(); Thread.currentThread().interrupt(); }

Q55. What happens when you submit after shutdown?

Answer: The executor rejects the task, typically by throwing RejectedExecutionException.

↑ Contents14

Shutdown and lifecycle · continued

Q56. Does shutdown wait for queued tasks?

Answer: No. It initiates orderly shutdown; use awaitTermination to wait for queued and running tasks to finish.

Q57. What should a finally block do in task code?

Answer: Release resources such as locks, streams, and permits. Cleanup must be safe whether the task completes normally, fails, or is interrupted.

Q58. Why should an ExecutorService be closed?

Answer: To release worker threads and associated resources. On modern Java, ExecutorService supports AutoCloseable and can be used with try-with-resources.

Q59. What is isTerminated()?

Answer: It returns true only after shutdown has been initiated and all tasks have completed following shutdown.

Q60. How do you handle application shutdown hooks?

Answer: Stop accepting work, initiate graceful shutdown, wait for a bounded period, then request interruption and preserve the shutdown thread's interrupt status.

ScheduledExecutorService

KEY TOPICS

Q61. What is ScheduledExecutorService used for?

Answer: It schedules one-shot delayed tasks and recurring tasks without manually creating Timer threads.

Q62. How do you schedule a task once after a delay?

Answer: scheduler.schedule(task, 5, TimeUnit.SECONDS); The returned ScheduledFuture can be cancelled or inspected.

Q63. What is scheduleAtFixedRate?

Answer: It targets executions at a fixed period measured from scheduled start times. If a run overruns, later runs may start late but do not overlap for the same periodic task.

Q64. What is scheduleWithFixedDelay?

Answer: It waits the specified delay after one execution terminates before starting the next execution.

Q65. Which is safer for variable-duration polling?

Answer: scheduleWithFixedDelay is often clearer because the delay begins after completion and avoids trying to maintain a fixed start-time cadence.

↑ Contents16

ScheduledExecutorService · continued

Q66. What happens if a periodic task throws?

Answer: Further executions of that periodic task are suppressed and its ScheduledFuture completes exceptionally. Catch expected exceptions inside the task if recurrence must continue.

Q67. How do you cancel a scheduled task?

Answer: Call ScheduledFuture.cancel(false) or cancel(true), depending on whether interruption of an active run is appropriate.

Q68. How do you stop a scheduler cleanly?

Answer: Call shutdown(), await termination, and if needed call shutdownNow(). Configure delayed/periodic-task shutdown policies deliberately.

Q69. Can scheduled tasks overlap?

Answer: A single periodic task submitted by scheduleAtFixedRate or scheduleWithFixedDelay does not overlap with itself, though different tasks can run concurrently.

Q70. How do you implement periodic health checks?

Answer: Use scheduleWithFixedDelay with a bounded task duration, exception handling, metrics, and cancellation during application shutdown.

Bulk execution and completion services

KEY TOPICS

Q71. What does invokeAll() do?

Answer: It submits a collection of Callables and returns Futures after all tasks complete, or after the specified timeout when using the timed overload.

Q72. What does invokeAny() do?

Answer: It returns the result of one successfully completed task, cancelling unfinished tasks when a successful result is obtained.

Q73. When is invokeAny useful?

Answer: For redundant equivalent operations, such as querying multiple replicas and accepting the first successful response, provided cancellation and side effects are safe.

Q74. What happens to invokeAll tasks on timeout?

Answer: The timed form cancels unfinished tasks when the timeout expires; inspect returned Futures for completion and cancellation.

Q75. How does CompletionService improve result handling?

Answer: It decouples submission order from completion order; take() retrieves the next completed Future.

↑ Contents18

Bulk execution and completion services · continued

Q76. Write a completion-order result loop.

Answer: Submit each Callable with completion.submit(task); repeat n times: Future<T> f = completion.take(); consume(f.get()).

Q77. Why might ordered Future.get calls be slow?

Answer: A slow first task blocks result processing even if later tasks already completed. CompletionService avoids this head-of-line waiting.

Q78. How do you implement first-success querying?

Answer: Submit independent Callable attempts, use invokeAny or CompletionService, enforce a deadline, and cancel remaining work after success.

Q79. Should invokeAll be used for huge unbounded collections?

Answer: Usually not without batching: it creates many tasks and Futures at once. Submit bounded batches or use a streaming producer.

Q80. How do you limit concurrent calls to a downstream service?

Answer: Use a dedicated bounded executor or a Semaphore around calls, with timeouts and explicit rejection/backpressure.

Concurrency correctness

KEY TOPICS

  • Concurrency correctness: essential API behaviour, implementation choices, and common interview trade-offs.
  • Focus on lifecycle, concurrency correctness, failure handling, and practical code design.

Q81. Why is shared mutable state risky in executor tasks?

Answer: Tasks may run concurrently and interleave reads/writes. Without synchronization or safe publication, results can be stale or updates lost.

Q82. How do you safely count completed tasks?

Answer: Use AtomicInteger.incrementAndGet(), LongAdder for high-contention statistics, or a synchronized/locked design when compound invariants are needed.

Q83. Why is incrementing a volatile int not atomic?

Answer: volatile guarantees visibility and ordering, not atomic read-modify-write. Two threads can read the same value and overwrite each other's increments.

Q84. How do you safely publish task input?

Answer: Submit immutable input or establish a happens-before relationship through thread-safe queues, synchronization, volatile fields, or executor submission semantics.

Q85. Can two tasks execute in parallel in a fixed pool?

Answer: Yes, if at least two workers are available and the tasks are independent. A pool size of one serializes execution.

↑ Contents20

Concurrency correctness · continued

Q86. What is a race condition?

Answer: The outcome depends on timing/interleaving of concurrent operations, often because shared state is accessed without adequate coordination.

Q87. How do you avoid deadlock between tasks in the same small pool?

Answer: Avoid tasks blocking while waiting for child tasks queued to the same saturated pool. Use separate pools, nonblocking composition, or sufficient capacity.

Q88. What is thread confinement?

Answer: Keeping mutable state owned by one thread so no synchronization is needed for that state. Do not leak references to confined objects.

Q89. Why should tasks generally be idempotent?

Answer: Retries, timeouts, and uncertain completion can cause duplicate execution. Idempotent operations make repeated attempts safe.

Q90. How do you coordinate a group of tasks?

Answer: Use higher-level constructs such as CountDownLatch, CyclicBarrier, Phaser, CompletableFuture, or structured concurrency where available.

Q91. How do you retrieve a task exception from submit()?

Answer: Call Future.get() and inspect the cause of ExecutionException.

Q92. Why might an UncaughtExceptionHandler not see exceptions from submit()?

Answer: The FutureTask wrapper captures task exceptions and stores them in the Future instead of letting them escape the worker thread.

Q93. How do you log failures in a pool?

Answer: Wrap tasks or use a custom FutureTask.done(), inspect Futures, and record task identity, duration, failure cause, and correlation ID.

Q94. What is afterExecute()?

Answer: A protected ThreadPoolExecutor hook called after a task completes. For FutureTask, inspect the Future because failures may be captured rather than thrown.

Q95. How do you name worker threads?

Answer: Provide a custom ThreadFactory that assigns descriptive names, daemon status if appropriate, and an uncaught exception handler.

↑ Contents22

Exception handling and observability · continued

Q96. Why are daemon threads not a substitute for shutdown?

Answer: The JVM may exit while daemon work is unfinished. Explicit lifecycle management is needed for reliable completion and cleanup.

Q97. What metrics matter for an executor?

Answer: Active workers, pool size, queue depth and age, completed/rejected tasks, task duration, wait time, failures, and shutdown state.

Q98. How do you propagate a diagnostic context?

Answer: Capture needed context at submission and restore/clear it around task execution; do not assume ThreadLocal values automatically follow tasks.

Q99. What is the risk of ThreadLocal in pooled threads?

Answer: Workers are reused, so values can leak between tasks unless removed in finally blocks. Prefer explicit context passing where practical.

Q100. How do you distinguish queue wait time from execution time?

Answer: Timestamp at submission and at task start/end; queue wait is start minus submit, execution time is end minus start.

Q101. What is CompletableFuture?

Answer: A Future that can be explicitly completed and composed with asynchronous stages, callbacks, and error-handling operations.

Q102. How do you runAsync with a custom executor?

Answer: CompletableFuture.runAsync(() -> doWork(), executor); This avoids relying on the common pool.

Q103. How do you supply an asynchronous result?

Answer: CompletableFuture.supplyAsync(() -> loadValue(), executor) returns CompletableFuture<T>.

Q104. Difference between thenApply and thenApplyAsync?

Answer: thenApply may run in the thread completing the prior stage; thenApplyAsync schedules the continuation, using the default async facility or a supplied executor.

Q105. How do you combine two independent futures?

Answer: Use thenCombine(other, (a, b) -> combine(a, b)) after both stages complete.

↑ Contents24

CompletableFuture with executors · continued

Q106. How do you wait for several futures?

Answer: Use CompletableFuture.allOf(f1, f2, f3).join(), then retrieve each result. allOf itself completes with Void.

Q107. How do you accept the first completed future?

Answer: Use anyOf(f1, f2, ...), which completes with the first completion, whether normal or exceptional.

Q108. How do you handle CompletableFuture errors?

Answer: Use exceptionally for fallback, handle for success/failure transformation, or whenComplete for side effects while preserving the outcome.

Q109. How do you apply a timeout?

Answer: Use orTimeout(duration, unit) to complete exceptionally on timeout, or completeOnTimeout(defaultValue, duration, unit) for a fallback.

Q110. Why pass an explicit executor to async stages?

Answer: It controls isolation, capacity, naming, and workload-specific tuning; the common pool may be shared with unrelated tasks.

Q111. What is ThreadFactory?

Answer: A factory abstraction used by executors to create worker threads with controlled naming, daemon settings, priority, and handlers.

Q112. How do you create named threads?

Answer: Implement newThread(Runnable r) and return new Thread(r, "orders-worker-" + sequence.incrementAndGet()).

Q113. Should worker threads usually be daemon threads?

Answer: For server-side work, usually use non-daemon workers and shut them down explicitly. Daemon status depends on whether unfinished work may be abandoned at JVM exit.

Q114. How do you set an UncaughtExceptionHandler?

Answer: Call thread.setUncaughtExceptionHandler((t, e) -> log(t.getName(), e)) inside the ThreadFactory.

Q115. What is beforeExecute() used for?

Answer: A ThreadPoolExecutor hook for per-task setup such as timing or context initialization. Ensure setup cannot leave worker state corrupted.

Q116. What is terminated() used for?

Answer: A ThreadPoolExecutor hook invoked after the executor has fully terminated; useful for final cleanup or lifecycle notification.

Q117. How can you customize FutureTask?

Pool sizing and performance

KEY TOPICS

  • Pool sizing and performance: essential API behaviour, implementation choices, and common interview trade-offs.
  • Focus on lifecycle, concurrency correctness, failure handling, and practical code design.

Q121. How do you size a CPU-bound pool?

Answer: A starting point is near the number of available processors, then benchmark. Account for container limits and other CPU consumers.

Q122. How do you size an I/O-bound pool?

Answer: Estimate based on target concurrency, downstream limits, and time spent waiting; use bounded queues and load tests rather than a universal formula.

Q123. What does availableProcessors() return?

Answer: The number of processors available to the JVM, which may reflect container/runtime constraints; it is a sizing input, not a guaranteed optimal pool size.

Q124. Why can too many threads hurt performance?

Answer: Context switching, memory for stacks, contention, cache disruption, and downstream overload can outweigh parallelism benefits.

Q125. What is queue latency?

Answer: The time a task waits between submission and execution start. It often reveals saturation before tasks fail.

↑ Contents28

Pool sizing and performance · continued

Q126. How do you prevent a slow task from monopolizing a pool?

Answer: Use deadlines, isolate slow/blocking work, bound concurrency, and avoid mixing long blocking jobs with latency-sensitive tasks.

Q127. What is head-of-line blocking?

Answer: A slow earlier item delays later work even if later tasks could finish quickly; separate queues or completion-order consumption can help.

Q128. Why benchmark executor changes under realistic load?

Answer: Throughput and latency depend on task mix, contention, queue policy, CPU limits, and downstream behaviour. Microbenchmarks alone can mislead.

Q129. What is work stealing?

Answer: Workers in a ForkJoinPool can take tasks from other workers' deques, helping balance recursive fine-grained workloads.

Q130. When is ForkJoinPool appropriate?

Answer: For decomposable CPU-bound work with many smaller subtasks; avoid blocking operations unless using managed blocking or a separate executor.

Q131. Write code to run a Runnable in a fixed pool.

Answer: try (ExecutorService pool = Executors.newFixedThreadPool(4)) { pool.submit(() -> System.out.println("work")); } // Java 19+ AutoCloseable ExecutorService; close waits for orderly completion.

Q132. Write code to submit a Callable and print its result.

Answer: try (ExecutorService pool = Executors.newSingleThreadExecutor()) { Future<Integer> f = pool.submit(() -> 21 * 2); System.out.println(f.get()); }

Q133. Write code to run three independent tasks.

Answer: Use a pool with capacity at least three, submit each task, retain the Futures, and await them. Do not assume submission itself means completion.

Q134. Write code to return a value with a lambda.

Answer: Callable<String> c = () -> "done"; Future<String> f = pool.submit(c); String result = f.get();

Q135. Write code to enforce a result timeout.

Answer: try { return future.get(2, TimeUnit.SECONDS); } catch (TimeoutException e) { future.cancel(true); throw e; }

Q137. Write code to count task completions.

Advanced coding scenarios

Q141. Implement a bounded executor for API calls.

Answer: new ThreadPoolExecutor(8, 16, 30, SECONDS, new ArrayBlockingQueue<>(200), threadFactory, new AbortPolicy()). Choose values from load tests and define caller-visible rejection handling.

Q142. Implement graceful shutdown with interruption.

Answer: Call shutdown; awaitTermination; if timed out call shutdownNow; on InterruptedException call shutdownNow and restore the interrupt flag.

Q143. Implement first successful result from several services.

Answer: Use invokeAny on equivalent Callables with a timeout. Ensure attempts are idempotent and cancellation does not leave unsafe side effects.

Q144. Implement a fan-out/fan-in operation.

Answer: Submit independent child tasks, then combine their Futures or use CompletableFuture.allOf and collect results after all complete.

Q145. Implement retry with backoff.

Answer: Schedule retries with bounded attempts and exponential delay plus jitter. Do not sleep while occupying a scarce worker; make the operation idempotent.

Advanced coding scenarios · continued

Q146. Implement a task deadline.

Answer: Compute an absolute deadline at submission and pass remaining time to each downstream call; cancel on expiry and avoid resetting the full timeout at every layer.

Q147. Implement per-customer task ordering.

Answer: Partition customers across serial executors or use keyed serial queues. Ensure bounded key cardinality, cleanup, and fairness.

Q148. Implement priority task execution.

Answer: Use a PriorityBlockingQueue with Comparable tasks or a wrapper; note it is unbounded by default and priority tasks can starve lower priorities.

Q149. Implement task deduplication.

Answer: Maintain a concurrent map from task key to in-flight CompletableFuture; reuse the existing future and remove it on completion with careful race handling.

Q150. Implement a bounded producer-consumer pipeline.

Answer: Use a bounded BlockingQueue between producer and worker consumers; put/take provide backpressure and interruption-aware coordination.

Q151. Why should you avoid Executors.newFixedThreadPool for untrusted bursts?

Answer: Its unbounded queue can grow without limit. Prefer an explicitly configured ThreadPoolExecutor with bounded capacity and rejection policy.

Q152. Why is blocking on a Future inside a pool task risky?

Answer: If all workers block waiting for tasks queued to the same pool, no worker remains to run those tasks, causing thread-starvation deadlock.

Q153. Why should tasks not swallow InterruptedException?

Answer: It hides cancellation and shutdown requests, making the pool harder to stop and potentially leaving work running indefinitely.

Q154. Why is a global static executor problematic?

Answer: It can couple unrelated workloads, hide ownership, complicate tests and shutdown, and create contention. Prefer lifecycle-managed, purpose-specific executors.

Q155. Why should a task avoid holding a lock during blocking I/O?

Answer: It extends lock hold time and can stall unrelated threads. Capture state under lock, release it, then perform I/O.

Pitfalls and design review · continued

Q156. Why is an unbounded cached pool risky?

Answer: A burst of slow tasks can create many threads, exhausting memory or downstream capacity. Bound concurrency and queueing explicitly.

Q157. What is thread starvation?

Answer: Tasks cannot obtain execution time because workers are occupied, often by blocking or long-running tasks or by unfair scheduling.

Q158. How do you avoid resource leaks in tasks?

Answer: Use try-with-resources, finally blocks, bounded waits, cancellation handling, and explicit executor shutdown.

Q159. What should be considered when using virtual threads?

Answer: They make blocking concurrency cheaper, but do not remove downstream limits, CPU limits, synchronization bottlenecks, or the need for cancellation and resource bounds.

Q160. How do you choose between platform-thread pools and virtual threads?

Answer: Use pools for controlled CPU parallelism and isolation; consider virtual threads for large numbers of blocking tasks, while still bounding scarce resources such as DB connections.

Q161. What is ForkJoinPool?

Q162. What is RecursiveTask?

Q163. What is RecursiveAction?

Q165. What is the fork-compute-join pattern?

Answer: Fork one subtask, compute another directly, then join the forked task. This reduces unnecessary scheduling overhead.

Q171. What are virtual threads?

Answer: Lightweight threads managed by the JVM, intended to make thread-per-task blocking code scalable for many concurrent tasks.

Q172. How do you create a virtual-thread-per-task executor?

Answer: try (var executor = Executors.newVirtualThreadPerTaskExecutor()) { executor.submit(task); } This API is available in Java 21+.

Q173. Do virtual threads make CPU-bound code faster?

Answer: No. They improve scalability for blocking concurrency; CPU throughput remains limited by available processor capacity.

Q174. Should virtual threads be pooled?

Answer: Generally no. The intended model is one virtual thread per task; limit scarce downstream resources with semaphores or connection pools.

Q175. How do you bound database concurrency with virtual threads?

Answer: Use a Semaphore or the database connection pool's own capacity, acquiring a permit around the database operation.

Modern Java and virtual threads · continued

Q176. Can virtual threads be interrupted?

Answer: Yes. Interruption remains a cancellation signal, and tasks should respond cooperatively.

Q177. What is thread pinning?

Answer: A virtual thread may be unable to unmount from its carrier during certain operations, historically including some synchronized/blocking interactions; check the target JDK's current guidance.

Q178. Can ThreadLocal be used with virtual threads?

Answer: Yes, but large numbers of virtual threads can make per-thread state expensive. Consider scoped values where supported by the target JDK.

Q179. What executor abstraction is useful for structured concurrency?

Answer: StructuredTaskScope in preview/incubator releases depending on JDK version; verify the exact status and API for the Java version in use.

Q180. What is the key migration risk from pools to virtual threads?

Answer: Assuming cheap threads means unlimited downstream capacity. Preserve limits, timeouts, cancellation, observability, and overload controls.

Q181. How do you test asynchronous code deterministically?

Answer: Use latches, barriers, controlled test executors, and bounded timeouts rather than arbitrary Thread.sleep calls.

Q182. How can CountDownLatch help in a test?

Answer: Have each task count down in finally and let the test await the latch with a timeout before asserting outcomes.

Q183. Why avoid Thread.sleep in concurrency tests?

Answer: It makes tests timing-dependent and flaky. Synchronize on observable events instead.

Q184. How do you detect a stuck executor?

Answer: Monitor queue age, active count, task duration, thread dumps, and progress counters; identify workers blocked on I/O, locks, or Future.get.

Q185. What does a thread dump reveal?

Answer: Worker states, stack traces, lock ownership/waiting, blocked I/O, deadlocks, and whether tasks are progressing.

Q186. How do you test rejection behaviour?

Answer: Use a tiny pool and bounded queue, block workers with latches, submit beyond capacity, then assert the configured handler's behaviour.

Q187. How do you test cancellation?

Answer: Use a task that waits on an interruptible latch; cancel(true) and assert it observes interruption and performs cleanup.

Q188. How do you test graceful shutdown?

Architecture and interview scenarios

Q191. Design an executor for image resizing.

Answer: Use a CPU-sized bounded pool, bounded queue, input-size limits, rejection/backpressure, and metrics. Avoid unbounded task submission.

Q192. Design an executor for outbound HTTP calls.

Answer: Use a dedicated bounded-concurrency executor or virtual threads with a semaphore, connection limits, request deadlines, retries with jitter, and circuit breaking.

Q193. Design a background email sender.

Answer: Persist work durably, dispatch through bounded workers, make sends idempotent where possible, retry transient failures, and expose dead-letter/failed status.

Q194. Design a scheduled cleanup service.

Answer: Use ScheduledExecutorService, fixed-delay scheduling, bounded cleanup batches, exception handling, and graceful cancellation on shutdown.

Q195. Design parallel aggregation of microservice responses.

Answer: Fan out using independent tasks, propagate a shared deadline, collect completion-order results, apply partial-result policy, and cancel outstanding calls.

Architecture and interview scenarios · continued

Q196. How would you isolate tenant workloads?

Answer: Use per-tenant quotas or fair admission control and avoid unbounded per-tenant pools. Consider partitioned queues with bounded total capacity.

Q197. How do you preserve ordering while scaling workers?

Answer: Partition by key so each key maps to a serial lane, while different keys execute concurrently. Handle lane lifecycle and bounded queues.

Q198. How do you prevent duplicate background jobs?

Answer: Use durable unique job keys or distributed idempotency, plus in-process in-flight deduplication as an optimization rather than the sole guarantee.

Q199. How do you handle poison tasks?

Answer: Limit retries, classify permanent versus transient failures, quarantine or dead-letter poison work, and keep failures from blocking the queue.

Answer: Explicit ownership, bounded resources, clear rejection semantics, deadlines, cooperative cancellation, failure visibility, metrics, tests, and graceful shutdown.
