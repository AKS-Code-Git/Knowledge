Guide overview

1. Core Java Language

1. == vs .equals()

== compares primitive values, but for references it asks whether both variables point to the same object. equals() compares logical equality when a class overrides it. String overrides equals(), so new String("x").equals("x") is true while the references may not be identical. Integer values from -128 through 127 are commonly cached, so boxed comparisons with == can appear true in that range; never rely on this. Compare wrappers with equals() or unbox safely.

2. String immutability

A String cannot be changed after construction; operations produce a new String. Immutability supports safe sharing, String-pool reuse, stable hash codes for map keys, thread safety, and security-sensitive values such as class names or paths. For repeated modifications, use StringBuilder instead.

3. String pool, literals, new, intern()

String literals and compile-time constants are pooled. new String("cat") explicitly creates a distinct String object (though the literal is pooled). intern() returns the canonical pooled representation: use it only when canonicalization is useful, not as a default optimization.

4. StringBuilder vs StringBuffer

Both are mutable character sequences. StringBuilder is not synchronized and is usually faster for single-threaded construction. StringBuffer synchronizes its methods for thread-safe individual operations, at a cost. Synchronization of separate calls does not automatically make a multi-call workflow atomic.

5. Primitive types vs wrappers

Primitives (int, long, boolean, etc.) hold values and cannot be null; wrappers (Integer, Long, Boolean) are objects and can be null, work with generics/collections, and expose utility methods. Autoboxing converts between them. Unboxing null throws NullPointerException; wrapper == can compare identity; boxing in loops can allocate or add overhead. Prefer primitives unless object semantics are needed.

6. final vs finally vs finalize()

final prevents reassignment, overriding, or subclassing depending on context. finally is a cleanup block that normally runs after try/catch, though process termination or severe VM failure can prevent it. finalize() was an unreliable finalization mechanism and is deprecated for removal; use try-with-resources and explicit cleanup instead.

7. Access modifiers

public: accessible wherever the declaring type is accessible. protected: same package plus subclasses (cross-package subclass access has additional receiver rules). package-private/default: same package only. private: within the declaring top-level class, including its nested classes. Top-level classes can be public or package-private, not private/protected.

8. static keyword

A static field belongs to the class, not each instance. Static methods have no this/super instance context and cannot directly access instance members. Static blocks initialize class-level state. Static nested classes do not require an enclosing instance. Static methods are hidden, not overridden.

9. Initializer execution order

On first active use, class initialization runs superclass static initialization first, then static field initializers/blocks in textual order. Object construction initializes superclass instance state first; then subclass instance field initializers/instance initializer blocks in textual order, followed by the constructor body. Constructor chaining affects which constructor body executes, not the basic superclass-before-subclass initialization order.

10. Pass-by-value

Java is always pass-by-value. For an object parameter, the copied value is a reference. A method can mutate the referenced object and the caller sees that mutation, but assigning the parameter to a different object does not reassign the caller's variable.

11. Varargs

A declaration such as void log(String... items) receives an array and permits zero or more arguments. Varargs must be the final parameter. Overload resolution prefers applicable fixed-arity methods before variable-arity methods, which can make overloads surprising; avoid ambiguous overload sets and be careful with null, which may mean a null array.

12. instanceof and pattern matching

Traditional x instanceof String checks runtime type. Java 16 pattern matching allows if (x instanceof String s) { ... }, combining test and cast. The pattern variable is in scope only where the compiler can prove the test succeeded; null returns false.

13. Ternary and switch expressions

The ternary operator condition ? a : b chooses one of two expressions. A switch statement controls flow; a switch expression returns a value and can use arrow labels and yield for block arms. Switch expressions became final in Java 14. Ensure cases are exhaustive and understand fall-through in traditional colon-style switches.

14. Text blocks

Text blocks use triple quotes to represent multiline strings, reducing escaping for JSON, SQL, and templates. Incidental indentation is stripped according to the closing delimiter and content indentation. They are still String literals, not a template engine.

15. var / local inference

Since Java 10, var asks the compiler to infer a local variable's static type from its initializer. It is not dynamic typing. It requires an initializer and cannot be used for fields, method parameters, or return types. Use it when the inferred type is clear.

16. Records

Records (Java 16+) are concise data carriers: components generate a canonical constructor, accessors, equals, hashCode, and toString. They are shallowly immutable: component fields are final, but a referenced mutable object can still change. Records cannot extend arbitrary classes, though they can implement interfaces and define validation or extra methods.

17. Sealed classes

Sealed classes/interfaces restrict direct subtypes using permits, with permitted subtypes declared final, sealed, or non-sealed. They make domain hierarchies explicit and can improve exhaustive pattern matching. Use them when the set of variants is intentionally controlled.

18. Enums

Enums are type-safe fixed sets of instances. They can implement interfaces, have fields and methods, and define constructors (implicitly private). Enum constructors cannot be called directly. Enums are often excellent singletons and can carry behavior per constant.

19. Nested classes

A static nested class has no implicit enclosing instance. A non-static inner class captures an enclosing instance. Local classes are declared in a method/block; anonymous classes create a one-off subclass or implementation. Captured local variables must be final or effectively final. Choose the simplest construct that expresses the relationship.

20. Array vs ArrayList

Arrays have fixed length and can hold primitives or references. ArrayList is a resizable generic collection of references, offers collection APIs, and cannot directly store primitives (boxing is used). Arrays offer low overhead and can be covariant; generic collections provide stronger type checking. ArrayList indexed access is O(1), append amortized O(1), and middle insert/remove O(n).

2. OOP Concepts

↑ ContentsStudy page 4

21. Four pillars

Encapsulation: hide state behind methods and invariants. Abstraction: expose essential operations while hiding implementation. Inheritance: derive a subtype from a base type for a genuine “is-a” relationship. Polymorphism: call overridden behavior through a base/interface reference. Example: Shape s = new Circle(); s.area() dispatches to Circle at runtime.

22. Overloading vs overriding

Overloading uses the same method name with different parameter lists and is resolved at compile time; return type alone cannot overload a method. Overriding replaces inherited instance behavior with a compatible signature and is dispatched at runtime. An override cannot reduce visibility or broaden checked exceptions; it may return a subtype (covariant return).

23. Abstract class vs interface

Use an abstract class for shared state, constructors, protected helpers, or a common implementation among closely related types. Use an interface for a capability/contract that unrelated classes can implement; a class can implement multiple interfaces. Interfaces can declare abstract, default, static, and private helper methods (modern Java), but no instance constructors or per-object instance fields.

24. Interface constructors and methods

An interface cannot be instantiated and has no constructor. Fields are implicitly public static final constants. Default methods provide inherited instance behavior; static methods belong to the interface and are called through its name. Private interface methods can share code among defaults/static methods.

25. Default-method diamond

If two unrelated interfaces provide the same default method, the implementing class must override it and resolve the conflict. A class method takes precedence over an interface default; a more-specific subinterface default takes precedence over a less-specific parent. Use InterfaceName.super.method() to explicitly invoke an inherited default where legal.

26. Composition vs inheritance

Composition means one object delegates to or contains other objects; it avoids fragile base-class coupling and supports swapping behavior. Inheritance is appropriate for a substitutable “is-a” relationship. Favor composition when reuse is the main goal, but do not prohibit inheritance when subtype semantics are sound.

27. this() vs super()

this(...) invokes another constructor in the same class; super(...) invokes a superclass constructor. A constructor can use only one of them as its first explicit constructor invocation (subject to newer Java flexible-constructor rules). Chaining avoids duplicated initialization; ensure a chain terminates at a constructor that initializes the object.

28. Private constructors

Yes. A private constructor prevents external instantiation and is used in utility classes, controlled factories, and Singleton patterns. Reflection can sometimes bypass ordinary access controls, so a private constructor alone is not a universal security boundary.

29. Static method hiding

Static methods are selected using the compile-time reference type and can be hidden by a subclass method of the same signature. Instance overrides are selected by the runtime object's class. Static methods cannot override instance methods or vice versa.

30. Covariant returns

An overriding method may return a subtype of the original method's reference return type, e.g. base method returns Animal and override returns Dog. This improves type specificity without changing the method's parameter signature.

31. Object methods

equals() defines logical equality; hashCode() supports hash-based collections; toString() provides a readable representation; getClass() returns the runtime Class; clone() is protected and shallow by default, and Cloneable has unusual legacy semantics. Prefer explicit copy constructors/factories over clone for most designs.

32. equals/hashCode contract

Equal objects must have equal hash codes. Unequal objects may share a hash. equals should be reflexive, symmetric, transitive, consistent, and false for null. Override both together; otherwise HashMap/HashSet may fail to find logically equal keys.

33. Shallow vs deep copy

A shallow copy duplicates the outer object but shares referenced children. A deep copy recursively duplicates the relevant mutable object graph. Copy constructors or static factories make intended semantics clear. Cloneable does not automatically perform deep copying; document handling of cycles and immutable shared values.

34. Marker interfaces

A marker interface has no methods but signals a property to frameworks/runtime. Serializable enables Java serialization; Cloneable signals Object.clone may make a field copy; Remote historically marks remote objects. Annotations often provide metadata more flexibly, but marker interfaces can participate in type checking.

3. Collections Framework

35. Hierarchy

Collection is the root for groups: List preserves order and allows duplicates; Set enforces uniqueness; Queue models pending elements; Deque supports both ends. Map maps keys to values but is not a subtype of Collection. Choose by required semantics, not merely implementation familiarity.

36. ArrayList vs LinkedList

ArrayList: O(1) indexed get/set, amortized O(1) append, O(n) insertion/removal in the middle due to shifting. LinkedList: O(n) indexed access; O(1) insert/remove once a node/iterator position is known, but locating that position costs O(n). ArrayList usually has better locality and is the default choice; LinkedList is useful only for particular deque/list workloads.

37. HashMap internals

HashMap hashes a key and maps the hash to a bucket. Collisions are handled by a bucket structure; modern Java uses linked nodes and may treeify sufficiently large collision bins under capacity/threshold conditions. Average get/put is O(1), worst-case behavior depends on collisions and implementation. Keys must obey equals/hashCode; mutable key fields can make entries unreachable.

38. HashMap vs Hashtable vs ConcurrentHashMap

HashMap is unsynchronized and allows one null key and null values. Hashtable is legacy synchronized and disallows nulls. ConcurrentHashMap supports concurrent access with finer-grained coordination/CAS, disallows nulls, and provides atomic operations such as computeIfAbsent. Prefer ConcurrentHashMap for shared concurrent maps.

39. HashMap vs TreeMap vs LinkedHashMap

HashMap gives no iteration-order guarantee and average O(1) operations. LinkedHashMap maintains insertion order (or access order when configured), useful for predictable iteration/LRU designs. TreeMap keeps keys sorted using natural order or a Comparator, with O(log n) operations; keys must be mutually comparable under that ordering.

40. Load factor/resizing

Load factor is the threshold ratio of entries to bucket capacity; the common default is 0.75. When size exceeds capacity × load factor, HashMap grows and redistributes entries. A larger factor saves memory but may increase collisions; a smaller one uses more memory but may reduce collisions. Pre-size when expected size is known and avoid unnecessary resizing.

41. Set variants

HashSet offers average O(1) membership with no order guarantee. LinkedHashSet preserves insertion order with extra linked bookkeeping. TreeSet maintains sorted order with O(log n) operations and comparator/natural-order constraints. All depend on consistent equality/order semantics.

42. Comparable vs Comparator

Comparable defines a type's natural order through compareTo(T). Comparator defines external/custom ordering through compare(a,b), allowing multiple sort orders. A comparator should be consistent and ideally consistent with equals when used in sorted sets/maps.

43. Sorting collections/maps

Use list.sort(comparator) or Collections.sort. Build comparators with Comparator.comparing(Person::name).thenComparing(Person::age); reverse with reversed(). Maps can be sorted by copying entries to a list or using TreeMap for key order. Sorting n items typically costs O(n log n).

44. Iterator/ListIterator/Enumeration

Iterator traverses forward and may support remove. ListIterator works on lists in both directions and supports add/set. Enumeration is a legacy read-only traversal interface. Prefer Iterator or enhanced for-loop for modern code.

45. Fail-fast vs concurrent iteration

Many standard collection iterators are fail-fast on a best-effort basis and may throw ConcurrentModificationException after structural modification outside the iterator. This is a bug-detection aid, not a synchronization guarantee. Concurrent collections provide weakly consistent or snapshot-style iteration; “fail-safe” is informal, not a formal Java contract.

46. Queue/Deque/PriorityQueue

Queue typically processes FIFO; Deque supports insertion/removal at both ends and can act as a queue or stack. PriorityQueue retrieves the least element by default (according to ordering), not insertion order; peek is O(1), insertion/removal O(log n). Select based on ordering requirements.

47. Stack vs Deque

Legacy Stack extends Vector and inherits synchronization and design baggage. Prefer Deque<T> stack = new ArrayDeque<>() with push/pop/peek for a typical LIFO stack. ArrayDeque does not permit null elements.

48. Immutable collections

List.of/Set.of/Map.of create unmodifiable collections and reject nulls; mutation throws UnsupportedOperationException. Collections.unmodifiableList(list) is a read-only view of the original list, so changes through another reference remain visible. Neither means the contained objects themselves are deeply immutable.

49. Arrays.asList gotchas

Arrays.asList(array) returns a fixed-size list backed by the array. set is supported and changes the array, but add/remove are not supported. With primitive arrays, the result is a list containing one primitive-array object, not a list of boxed elements. Use new ArrayList<>(...) for a resizable copy.

50. Collections utilities

Collections provides sort, reverse, shuffle, binarySearch, max/min, frequency, and unmodifiable/synchronized wrappers. binarySearch requires a list sorted under the same ordering and returns a negative insertion-point encoding when absent. Utility methods often mutate the supplied collection; check API contracts.

4. Generics

51. Type erasure

Generic type parameters are mostly erased at runtime; List and List share the same raw runtime class. This supports backward compatibility but prevents checks such as instanceof List<String> and direct creation of T arrays. Compiler inserts casts and bridge methods where needed.

52. Bounded types

A bound such as <T extends Comparable<T>> limits T to types that can be compared to T. For multiple bounds, a class bound must come first, followed by interfaces. Bounds allow generic code to call methods guaranteed by the bound.

↑ ContentsStudy page 7

53. Wildcards

means an unknown type. accepts T or subtypes and is useful for reading values as T; accepts T or supertypes and is useful for writing T values. Wildcards express variance at the use site; generic classes themselves are invariant.

54. PECS

Producer Extends, Consumer Super: if a structure produces T values for you, use ? extends T; if you put T values into it, use ? super T. For both reading and writing the exact T, use a concrete type parameter. Example: Collections.copy(dest, src) consumes into dest and produces from src.

55. Generic arrays

Creating new T[] is prohibited because the runtime cannot know T's erased component type, and arrays enforce runtime component checks. Prefer List, or accept a Class/array factory when an actual array is required. Casting Object[] to T[] is unsafe unless the runtime type truly matches.

56. Raw types

A raw List omits its type argument and disables generic checking, allowing heap pollution and runtime ClassCastException. Use parameterized types and wildcards instead. Raw types remain for legacy interoperability, but should be isolated and documented.

57. Generic methods/classes

A generic class declares type parameters on the class, e.g. Box. A generic method declares its own parameters before the return type, e.g. <T> T first(List<T> xs). Method type parameters are inferred from arguments/target context when possible.

5. Exception Handling

58. Checked vs unchecked

Throwable splits into Error and Exception. Errors usually represent serious JVM/environment problems and are generally not caught. RuntimeException and its subclasses are unchecked; other Exception subclasses are checked and must be caught or declared. Use checked exceptions for recoverable conditions callers are expected to handle; use unchecked for programming errors or APIs where recovery is not mandated.

59. throw vs throws

throw raises a specific exception object at runtime. throws declares possible exception types in a method signature, transferring handling responsibility to callers for checked exceptions. Example: throw new IOException("failed") versus void read() throws IOException.

60. Multi-catch

catch (IOException | SQLException e) handles alternatives with one block. Alternatives cannot be related by subclassing, and the multi-catch parameter is effectively final. Use separate catches when recovery differs.

61. Try-with-resources

Resources implementing AutoCloseable are closed automatically in reverse declaration order, including when an exception occurs. Close failures are generally suppressed when another exception is already propagating and can be inspected via getSuppressed(). Prefer this to manual finally cleanup.

62. Exception in finally

If finally throws or returns, it can replace the exception/return already in flight, potentially hiding the original failure. Avoid return/throw from finally. Try-with-resources preserves a primary exception and records close failures as suppressed exceptions.

63. Custom exceptions

Create a custom exception when it adds meaningful domain context or enables callers to distinguish a failure category. Extend Exception for checked behavior or RuntimeException for unchecked behavior. Include a useful message and preserve the cause; avoid creating a new class for every trivial case.

↑ ContentsStudy page 8

64. Exception chaining

Wrap a lower-level exception with domain context while preserving it as the cause, e.g. throw new ServiceException("Could not load account", cause). initCause() exists for legacy cases; constructors accepting a cause are clearer. Do not discard stack traces or causes.

65. Best practices

Do not swallow exceptions silently. Catch the narrowest useful type, log at an appropriate boundary, and either recover or propagate. Avoid catching Throwable and broad Exception without a concrete reason. Do not log and rethrow at every layer, which creates duplicate logs. Never expose secrets in exception messages.

6. Multithreading & Concurrency

66. Thread/Runnable/Callable

Thread represents an executing thread. Runnable's run() returns void and cannot declare checked exceptions; Callable returns a value and can throw exceptions, usually submitted to an ExecutorService to obtain a Future. Prefer separating task from thread management with executors.

67. Thread lifecycle

Java states are NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, and TERMINATED. RUNNABLE includes both actually running and ready-to-run states. BLOCKED means waiting to acquire a monitor; WAITING is indefinite coordination; TIMED_WAITING has a timeout. State snapshots are diagnostic, not synchronization primitives.

68. synchronized

A synchronized instance method locks this; a static synchronized method locks the Class object. A synchronized block can lock a specific private lock object and narrow the critical section. Monitor unlock happens-before a later lock of the same monitor, providing mutual exclusion and visibility.

69. wait/notify vs sleep

wait(), notify(), and notifyAll() operate on an object's monitor and must be called while owning it. wait releases that monitor and should be used in a while-loop checking a condition; notify signals one waiter, notifyAll signals all. sleep pauses without releasing held locks. Prefer higher-level concurrency utilities when possible.

70. Deadlock

Deadlock occurs when threads wait cyclically for locks/resources. Prevention: acquire locks in a consistent global order, minimize nested locking, use timed tryLock where appropriate, and avoid callbacks while holding locks. Thread dumps can reveal cycles; design-level prevention is better than trying to recover after deadlock.

71. Livelock and starvation

Livelock: threads remain active but repeatedly yield/retry without progress. Starvation: a thread rarely gets CPU or a needed lock/resource. Use randomized backoff, fair locks when justified, bounded retries, and balanced scheduling; fairness can reduce throughput.

72. volatile

A volatile write becomes visible to subsequent reads of the same variable and establishes happens-before ordering. It does not make compound operations such as count++ atomic. Use it for simple state flags or safely published immutable references; use locks or atomics for read-modify-write coordination.

73. Atomic classes/CAS

AtomicInteger/AtomicLong provide atomic operations using compare-and-set (CAS) and memory-order guarantees. CAS updates only if the value still matches an expected value; loops may retry under contention. Atomicity of one variable does not make a multi-variable invariant atomic.

74. ReentrantLock vs synchronized

Both provide mutual exclusion and reentrancy. ReentrantLock adds tryLock, interruptible acquisition, optional fairness, and multiple Conditions, but must be unlocked in finally. synchronized is simpler and automatically releases the monitor on exit; use Lock features only when needed.

75. ReadWriteLock

A ReadWriteLock permits multiple concurrent readers or one exclusive writer. It can help read-heavy workloads, but lock overhead and writer contention may make it slower than synchronized/ordinary locks for small critical sections. Benchmark realistic traffic.

76. Executor framework

Executor separates task submission from execution policy. ExecutorService supports shutdown, submit, and Future results. Choose bounded queues and explicit rejection policies for production; unbounded queues can cause memory growth. Shut down services gracefully and await termination when appropriate.

77. Future and CompletableFuture

Future represents a result that may not yet be ready and commonly blocks on get(). CompletableFuture supports dependent stages, composition, exception handling, and asynchronous pipelines. Use thenCompose to flatten async stages, thenCombine to combine independent results, and handle/exceptionally for failures. Async methods may use the common pool unless an executor is supplied.

78. BlockingQueue

BlockingQueue offers thread-safe producer-consumer handoff; put/take block when full/empty. Bounded queues apply backpressure and limit memory. Poison-pill/sentinel items can signal shutdown when designed carefully. Prefer this over hand-written wait/notify for many producer-consumer tasks.

79. ThreadLocal

ThreadLocal gives each thread its own value, often used for request context or legacy per-thread state. In pooled threads, values can persist between tasks; remove them in finally to prevent data leakage and memory retention. Avoid using it to hide dependencies or store large objects indefinitely.

80. Latch/Barrier/Semaphore

CountDownLatch lets threads await a count reaching zero; it cannot be reset. CyclicBarrier lets a fixed group meet repeatedly at a barrier. Semaphore limits concurrent access using permits. Choose based on one-time completion, repeated rendezvous, or capacity limiting.

81. Thread-pool sizing

CPU-bound pools often start near the number of available processors. I/O-bound pools may be larger because tasks spend time waiting, but size depends on latency, resource limits, queueing, and downstream capacity. Measure throughput and tail latency; avoid blindly using huge pools or unbounded queues.

82. ConcurrentHashMap internals

Older ConcurrentHashMap implementations used segmented locking. Modern implementations use CAS and synchronized coordination on bins, with tree bins for heavy collisions. Do not depend on exact internal mechanics; rely on documented thread-safe operations. Compound workflows should use compute/merge/putIfAbsent rather than separate check-then-act calls.

83. Happens-before / JMM

Happens-before is a visibility/order guarantee: program order within a thread, monitor unlock-to-lock, volatile write-to-read, thread start/join rules, and safe publication mechanisms create edges. Without a happens-before relationship, another thread may see stale or inconsistent state. Avoid unsynchronized shared mutable state.

7. JVM & Memory Management

84. Heap vs stack

The heap stores objects and arrays and is managed by garbage collection. Each thread has a stack containing frames, local variables, and call state. References may live in stack frames while referenced objects live on the heap. Deep recursion can overflow a stack; retaining too many reachable objects can exhaust the heap.

↑ ContentsStudy page 10

85. Garbage collection

GC reclaims objects no longer reachable from GC roots. Mark-and-sweep identifies live objects and reclaims dead ones; compaction may reduce fragmentation. Generational collectors exploit the tendency for many objects to die young, separating young and old regions. GC is nondeterministic; do not rely on it to close resources.

86. GC types

Serial uses a single GC thread and suits small heaps/simple environments. Parallel GC prioritizes throughput using multiple workers. CMS was a low-pause concurrent collector removed in modern Java. G1 divides the heap into regions and targets pause-time goals. ZGC targets very low pauses, including large heaps. Availability and defaults depend on the JDK version; benchmark the actual workload.

87. Soft/Weak/Phantom references

Soft references may be cleared under memory pressure (not a reliable cache policy by themselves). Weak references do not keep referents alive and are used in structures such as WeakHashMap. Phantom references support post-mortem cleanup tracking via ReferenceQueue and require careful use; modern resource cleanup should usually use try-with-resources/Cleaner where appropriate.

88. Memory leaks

A Java leak means objects remain reachable unintentionally. Common causes: static collections, unbounded caches, listeners not deregistered, ThreadLocal values in pools, retained classloaders, and resources/buffers not released. Diagnose with heap dumps, dominator trees, allocation profiling, and retained-size analysis; fix ownership/lifecycle rather than forcing GC.

89. Class loading

Class loaders load classes lazily and typically use parent delegation. Bootstrap loads core classes; platform loader loads platform modules; application/system loader loads application classpath/module-path classes. “Extension ClassLoader” is legacy terminology from older Java versions. Class identity depends on both binary name and defining class loader.

90. Method area, Metaspace, PermGen

The JVM specification describes a method area conceptually. HotSpot used PermGen before Java 8; Java 8 replaced it with native-memory Metaspace for class metadata. Metaspace can still exhaust native memory, often due to classloader leaks or excessive generated classes.

91. OutOfMemoryError vs StackOverflowError

OutOfMemoryError indicates the JVM cannot allocate required memory (heap, metaspace, direct buffers, etc.). StackOverflowError usually results from excessive recursion or deep call chains. Investigate the exact error message and dump/profiling data; increasing a limit may mask rather than solve the root cause.

8. Java 8+ Functional Features

92. Lambdas

A lambda implements a functional interface—an interface with one abstract method. Syntax examples: (x) -> x * 2, () -> work(). Lambdas capture only final/effectively-final local variables. They improve concise behavior passing but should remain readable.

93. Built-in functional interfaces

Function<T,R> maps T to R; Predicate<T> tests T to boolean; Supplier<T> provides T; Consumer<T> accepts T and returns void; BiFunction<T,U,R> accepts two inputs and returns R. Primitive specializations such as IntPredicate/ToIntFunction can avoid boxing.

94. Method references

The four common forms are static method (Class::staticMethod), bound instance (object::method), unbound instance (Class::instanceMethod), and constructor (Class::new). Use when the method signature matches the target functional interface and it improves clarity.

95. Streams API

map transforms each element; filter keeps matching elements; reduce combines values; collect gathers into a container; flatMap maps each element to a stream and flattens the results. Streams describe a pipeline, not a data structure. Avoid side effects in intermediate operations and do not reuse a consumed stream.

96. Intermediate/terminal and laziness

Intermediate operations (map/filter/sorted) are lazy and return another stream. Terminal operations (collect/forEach/count/reduce) trigger traversal. Short-circuit operations such as findFirst/anyMatch may stop early. A stream pipeline normally executes once; use a fresh stream for another traversal.

97. Optional

Optional represents a value that may be absent and can reduce null checks in return APIs. orElse evaluates its argument eagerly; orElseGet invokes a supplier only when empty. Avoid calling get without a presence check, and avoid Optional for every field/parameter by default. Optional is not a replacement for all null handling.

98. Collectors

Collectors.toList gathers values (implementation/mutability guarantees are limited unless specified). groupingBy creates groups by key; partitioningBy splits into true/false groups; joining concatenates strings with optional delimiter/prefix/suffix. Use downstream collectors such as counting, mapping, and summarizingInt to aggregate within groups.

99. Parallel streams

Parallel streams split work across threads (often the common ForkJoinPool). They may help large, CPU-bound, independent workloads with efficient splitting; they often hurt small tasks, blocking I/O, ordered operations, or shared mutable state. Benchmark end-to-end and consider executor/resource contention.

100. Interface default/static methods

Default methods add inherited behavior without breaking existing implementations; static methods are utility operations associated with the interface. Conflicts follow class-wins, most-specific-interface-wins, otherwise class must resolve. This topic overlaps with OOP interface rules and is often asked in Java 8 interviews.

9. I/O, Serialization & Misc APIs

101. Serializable

Serializable is a marker interface for Java object serialization. serialVersionUID identifies a class version for compatibility checks. transient fields are excluded from default serialization. Native Java deserialization of untrusted data is dangerous; prefer safer formats and strict filtering when serialization is unavoidable.

102. Streams vs readers/writers

InputStream/OutputStream operate on bytes and suit binary data. Reader/Writer operate on characters and decode/encode bytes using a charset. Specify the charset explicitly (for example UTF-8) to avoid platform-dependent text corruption. Buffering can reduce I/O calls.

103. NIO vs IO

java.nio.file provides Path and Files for filesystem operations; channels/buffers support more flexible and sometimes non-blocking I/O. Traditional java.io streams are simple and still useful. NIO is not automatically faster in every workload; choose based on APIs, scalability, and blocking requirements.

104. HashMap keys and immutability

A key's hash/equality-relevant state should not change while it is in a HashMap. If mutation changes hashCode, lookup may search a different bucket and fail. Immutable key types such as String, Integer, or well-designed records are safer. If using a custom key, implement equals/hashCode consistently.

105. Reflection

Reflection uses Class, Field, Method, and Constructor metadata to inspect or invoke members at runtime. It powers frameworks, serializers, dependency injection, and testing tools. It can weaken encapsulation, complicate refactoring, and cost more than direct calls; modern access/module rules can restrict it. Cache reflective metadata when appropriate.

106. Annotations

@Override asks the compiler to verify an override; @Deprecated marks APIs to avoid; @FunctionalInterface validates a single-abstract-method interface. Custom annotations define metadata with @interface and may specify retention (SOURCE/CLASS/RUNTIME), target, and elements. An annotation has effect only when compiler/tool/framework/runtime code processes it.

10. Design Patterns

107. Singleton

Eager initialization is simple and thread-safe. Lazy initialization can use a static holder class. Double-checked locking requires a volatile instance and correct synchronization. An enum singleton is concise and robust against ordinary serialization/reflection pitfalls. Prefer dependency injection when global state is not necessary.

108. Factory / Abstract Factory

Factory encapsulates object creation behind a method or interface, hiding concrete classes from callers. Abstract Factory creates families of related products without specifying concrete classes. Use when creation rules vary or clients should depend on abstractions; avoid factories that add indirection without a real need.

109. Builder

Builder separates construction of a complex object from its representation and supports readable optional parameters. It is useful when constructors would have many parameters or invalid combinations must be prevented. Validate invariants in build() and consider immutable final products.

110. Observer

Observer defines a subject that notifies subscribers when state/events change. It supports event-driven designs but can create lifecycle leaks, hidden control flow, and ordering questions. Provide unsubscribe/disposal and define synchronous vs asynchronous delivery semantics.

111. Strategy

Strategy encapsulates interchangeable algorithms behind a common interface. Clients select behavior by composition instead of large conditional branches or subclass variants. Examples include pricing rules, sorting policies, or retry policies.

112. Decorator

Decorator wraps an object with the same interface and adds behavior before/after delegation. It composes features at runtime (buffering, logging, compression) without many subclasses. Ensure wrapper behavior and resource ownership remain clear.

113. Adapter

Adapter converts one interface into another expected by a client, allowing incompatible APIs to work together. It is useful for legacy systems, third-party libraries, and migrations. Keep translation at a boundary and avoid adapters that conceal major semantic mismatches.

11. Testing & Tooling

114. JUnit basics

JUnit tests use @Test and assertions such as assertEquals, assertTrue, assertThrows. JUnit 5 uses @BeforeEach/@AfterEach for per-test setup/cleanup; older JUnit 4 used @Before/@After. Tests should be isolated, deterministic, readable, and verify behavior rather than implementation details.

115. Mockito basics

Mockito creates mocks/stubs to isolate a unit from external collaborators. Stub with when(...).thenReturn(...), verify interactions only when interactions are part of the contract, and use argument captors sparingly. Mock boundaries such as network clients; do not mock simple value objects or everything in the system.

↑ ContentsStudy page 13

116. Unit vs integration tests

Unit tests focus on a small unit in isolation and are fast. Integration tests verify components work together across boundaries such as database, filesystem, messaging, or HTTP. A healthy suite uses many focused unit tests plus a smaller number of realistic integration/end-to-end tests.

12. Coding Problems — Approaches and Complexity

For each problem, the interview answer should include the key invariant, edge cases, and time/space complexity. These are solution blueprints rather than full standalone implementations; practice coding each in runnable Java.

Arrays and Strings

Two Sum

Use a map from value to index; for each x, look for target-x before inserting x. O(n) time, O(n) space. Clarify whether one or multiple answers are required.

Three Sum

Sort, fix one index, then use two pointers while skipping duplicates. O(n²) time; sorting may use O(log n) stack space.

Anagram check / Group anagrams

Normalize according to problem rules; compare character counts or sorted signatures. Group with a map from signature to list. Typically O(n·k) for count signatures or O(n·k log k) for sorting strings of length k.

Longest substring without repeating characters

Sliding window with last-seen indices; move left past duplicate characters. O(n) time, O(alphabet) space.

String compression / rotation check

Compression scans runs and emits character plus count; return original if compressed form is not shorter if specified. Rotation: equal lengths and (s1+s1).contains(s2) is a simple check; O(n) auxiliary string space.

Rotate array

Use reverse-all, reverse-first-k, reverse-rest for O(n) time and O(1) extra space; normalize k modulo n and handle empty arrays.

Merge intervals

Sort by start, then merge when next.start <= current.end. O(n log n) time.

Kadane's maximum subarray

Track best sum ending here and global best: current=max(x,current+x), best=max(best,current). O(n) time, O(1) space; initialize carefully for all-negative arrays.

Missing number / Duplicate number

Missing 0..n: XOR or arithmetic sum, O(n)/O(1); beware integer overflow. Duplicate: hash set is simple; if values are 1..n with constraints, Floyd cycle detection may be O(1) space.

Move zeroes

Stable write-pointer compacts nonzeros, then fills remaining positions with zero. O(n), O(1), preserves nonzero order.

Product of array except self

Prefix product then suffix product without division. O(n), O(1) extra beyond output; handles zeros naturally.

Hashing

First non-repeating character

Count frequencies, then scan original order for count 1. O(n) time, O(alphabet) or O(n) space.

Subarray sum equals K

Prefix sum p; count earlier prefix sums equal to p-k using a frequency map initialized with 0→1. O(n) time, O(n) space; works with negative values.

↑ ContentsStudy page 15

Longest consecutive sequence

Put values in a set; only start a run when x-1 is absent, then advance. Expected O(n) time, O(n) space.

Linked Lists

Reverse linked list (iterative/recursive)

Iterative prev/current/next pointer rewiring is O(n) time, O(1) space. Recursive version is O(n) time and O(n) call stack.

Detect/remove cycle (Floyd)

Slow moves one step, fast two; a meeting proves a cycle. To find entry, reset one pointer to head and move both one step. To remove, find entry and predecessor, then set predecessor.next=null. O(n) time, O(1) space.

Merge two/k sorted lists

Two sorted lists: dummy head and choose smaller node each step, O(n+m). For k lists, min-heap gives O(N log k), or divide-and-conquer merge.

Middle node / nth from end

Slow/fast pointers find middle. For nth from end, advance lead n steps then move both; define behavior when n exceeds length. O(n), O(1).

Palindrome linked list

Find midpoint, reverse second half, compare halves, optionally restore list. O(n) time, O(1) extra space.

Stacks and Queues

Valid parentheses

Push opening delimiters; each closer must match stack top; success requires empty stack. O(n), O(n) space.

Min stack

Store value and current minimum per entry, or maintain a second min stack. Push/pop/top/getMin all O(1), O(n) space.

Queue using stacks / stack using queues

Queue with two stacks: input stack for enqueue, output stack for dequeue, transfer only when output is empty; amortized O(1). Stack using queues rotates elements after insertion, O(n) push or pop depending on design.

Next greater element

Monotonic decreasing stack of indices; when a larger value arrives, resolve popped entries. O(n) time, O(n) space.

Sliding window maximum

Monotonic deque of indices; evict expired indices and smaller values from the back. O(n) time, O(k) space.

Trees

Inorder/preorder/postorder

DFS visits node in left-node-right, node-left-right, or left-right-node order. Recursive time O(n), stack O(h); iterative versions use explicit stacks.

Level-order traversal

BFS with a queue, processing the queue size at each level. O(n) time, O(width) space.

Validate BST

Carry strict lower/upper bounds down the tree, or perform inorder and require strictly increasing values. O(n) time, O(h) auxiliary.

↑ ContentsStudy page 16

Lowest common ancestor

For a general binary tree, recurse; if both sides return non-null, current node is LCA. For BST, compare target values to branch left/right. O(n) general, O(h) BST.

Diameter of binary tree

Postorder compute subtree heights; at each node update leftHeight+rightHeight. O(n), O(h) stack.

Serialize/deserialize

Use preorder with explicit null markers or level order; parse in exactly the same order. O(n) time/space. Define delimiter/escaping and malformed-input handling.

Balanced tree check

Postorder returns height or sentinel -1 when unbalanced; avoid recomputing heights. O(n), O(h).

Path sum

DFS subtracts node values from target; for root-to-leaf variants check at leaves. For all paths, backtrack a path list. O(n) for existence, output-dependent for enumerating paths.

Graphs

Number of islands

Treat land cells as vertices; DFS/BFS or union-find joins adjacent land. O(rows×cols) time, up to O(rows×cols) space.

Clone a graph

BFS/DFS with map original node→clone; register clone before visiting neighbors to handle cycles. O(V+E) time/space.

Topological sort

Kahn's algorithm uses indegrees and a queue; if output count < V, a cycle exists. DFS with three colors is another option. O(V+E).

Detect cycle directed/undirected

Directed: DFS visiting/active/done states or Kahn count. Undirected: DFS with parent or union-find. O(V+E) DFS; clarify self-loops and multiedges.

Connected components

Run DFS/BFS from each unvisited vertex and increment component count. O(V+E).

BFS/DFS traversal

BFS uses queue and explores by distance in unweighted graphs; DFS uses recursion/stack for depth exploration. O(V+E) with adjacency lists; mark visited when enqueuing/pushing.

Binary Search

Search rotated sorted array

At each step identify which half is sorted, then decide whether target lies in that half. O(log n) with distinct values; duplicates can degrade to O(n).

First/last occurrence

Use lower-bound and upper-bound binary searches; O(log n). Be precise about inclusive/exclusive bounds.

Search in 2D matrix

If rows are globally sorted as one flattened array, binary-search indices in O(log(rows×cols)); if rows and columns are sorted, staircase search is O(rows+cols). Clarify which property applies.

↑ ContentsStudy page 17

Kth smallest/largest

Options: size-k heap O(n log k), quickselect expected O(n) but worst O(n²), or sort O(n log n). For a BST, inorder yields sorted order.

Recursion and Backtracking

Permutations/subsets/combinations

Build a partial choice, recurse, then undo it. Use index advancement for combinations and used[] for permutations. Complexity is output-size dominated: subsets 2^n, permutations n!, combinations depend on n and k.

N-Queens

Place one queen per row; track used columns and diagonals (row-col and row+col). Backtrack on conflicts. Exponential worst-case; pruning is essential.

Combination sum

DFS over candidates while tracking remaining target; allow reuse by recursing at same index when rules permit, otherwise advance. Sort and prune candidates greater than remaining. Complexity depends on number of valid combinations.

Word search

DFS from matching cell, mark visited, explore four neighbors, then unmark. O(rows×cols×4^L) upper bound for word length L; pruning and frequency checks help.

Dynamic Programming

Fibonacci with memoization

Cache results so each state is computed once: O(n) time and O(n) memory. Iterative two-variable version is O(n) time and O(1) space.

Climbing stairs

ways[n]=ways[n-1]+ways[n-2] for steps of 1 or 2. O(n) time, O(1) space; state assumptions and base cases.

Longest common subsequence

dp[i][j] = 1+dp[i-1][j-1] if chars match, else max(top,left). O(mn) time and O(mn) space; memory can be reduced to O(min(m,n)) for length only.

Coin change

For minimum coins, dp[a]=min(dp[a],dp[a-coin]+1); unreachable amounts stay infinity. O(amount×coinCount) time. For number of combinations, loop coins outside amounts to avoid counting permutations.

0/1 Knapsack

dp[i][w] considers excluding or including item i if capacity allows. O(nW) time; 1D optimization iterates capacity downward so each item is used once.

Design and Implementation

LRU Cache

Use HashMap + doubly linked list for O(1) get/put; move accessed nodes to front and evict tail when over capacity. LinkedHashMap access-order mode is a compact Java option.

LFU Cache

Track key→node plus frequency→list and minFrequency; update frequency on access and evict least-recently-used among least-frequent keys. Expected O(1) operations with careful bookkeeping.

Rate limiter

Common algorithms: fixed window (simple, boundary bursts), sliding log (accurate but memory-heavy), sliding counter, token bucket (allows bursts within a rate), leaky bucket (smooth output). Define key, clock, distributed consistency, and overload behavior.

Parking lot

Model Vehicle, Spot, Level, Ticket, and pricing/payment policy. Define spot compatibility, allocation strategy, concurrency, entry/exit, and failure cases. Separate domain rules from storage/UI.

Implement HashMap

Use an array of buckets, hash spreading/index calculation, collision chains or trees, resize threshold, and correct equals/hashCode handling. Include null policy, generics, iteration, and fail-fast behavior if required.

Thread-safe Singleton

Use enum, eager static field, static holder idiom, or volatile double-checked locking. Explain class initialization guarantees and avoid unsafe lazy initialization.

TTL cache

Store value plus expiry timestamp; check expiry on reads and optionally clean lazily or with periodic maintenance. Define monotonic clock use, stale-entry behavior, capacity eviction, and thread safety.

Custom Iterator

Implement hasNext/next and throw NoSuchElementException after exhaustion. Define modification semantics; optionally implement remove or fail-fast modification counts.

Merge k sorted lists using heap

Insert each non-empty list head into a min-heap, repeatedly extract minimum and insert its successor. O(N log k) time, O(k) heap space.

13. Karat-Specific Practical Tips

Communicate clearly

Explain the approach before coding, state assumptions, and narrate meaningful decisions. If the interview is recorded/scored, clarity is part of the evaluation.

Expect follow-ups

A round may include one or two problems in 45–60 minutes, then ask for O(1) space, concurrency, or streaming support. First deliver a correct baseline, then improve it.

Clarify edge cases

Ask about empty/null input, duplicates, negative numbers, sortedness, mutation, output format, and constraints before implementation.

Write runnable Java

Include imports, correct signatures, compilable code, and avoid pseudocode when runnable Java is expected.

Test before finishing

Walk through a normal example and at least one edge case. Check off-by-one errors, overflow, and null/empty input.

Prepare behavioral examples

Have concise project stories covering your role, trade-offs, conflict, impact, and lessons learned.

A practical answer structure

1. Restate the problem and clarify constraints.

2. Describe a straightforward solution and its complexity.

3. Improve it if needed; explain the invariant/data structure.

4. Write compilable Java with clear names and boundary checks.

5. Dry-run a representative case and an edge case.

6. Discuss trade-offs and likely follow-up changes.

Version reminders

Common milestones in the checklist: var (Java 10), switch expressions (Java 14), text blocks (Java 15), pattern matching for instanceof and records (Java 16), and sealed classes (Java 17). Some JVM/GC internals and API defaults differ by JDK version; answer with the target runtime in mind.
