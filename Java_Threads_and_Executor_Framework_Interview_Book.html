Part 1 · Thread Foundations

Thread Fundamentals

KEY KNOWLEDGE

  • A thread is an independent path of execution inside a JVM process. All threads of a process share the heap and method area, but every thread owns its program counter and call stack. Java exposes threads through java.lang.Thread, and since Java 21 also through lightweight virtual threads.
  • Rule of thumb: threads give you concurrency (structuring work as independent tasks) and, on multi-core hardware, parallelism (tasks truly running at once). The price is shared mutable state, which must be protected.

Q1. What is a thread, and what does it share with other threads?

A thread is the smallest schedulable unit of execution. Threads in one JVM share the heap, static fields and loaded classes, but each has a private stack, program counter and thread-local storage.

Q2. How is a thread different from a process?

A process has its own address space and OS resources and is isolated from other processes. Threads live inside a process, share its memory, are cheaper to create and switch, but can corrupt each other's data if not synchronized.

↑ Contents6

Thread Fundamentals · continued

Q3. What is the difference between concurrency and parallelism?

Concurrency is about structuring a program to handle multiple tasks whose execution overlaps in time. Parallelism is about executing multiple tasks simultaneously on multiple cores. You can have concurrency on a single core.

Q4. What is the main thread?

The thread the JVM starts to run public static void main. The JVM stays alive until all non-daemon threads finish, not just main.

Q5. What does the JVM do when the main thread ends but other threads are still running?

Nothing special: the JVM keeps running until every non-daemon (user) thread has terminated. Only then does it shut down.

Q6. What is a daemon thread?

A service thread (like the garbage collector) that does not keep the JVM alive. When only daemon threads remain, the JVM exits and abruptly stops them without running finally blocks.

Q7. How do you mark a thread as daemon, and when must you do it?

Call setDaemon(true) before start(). Doing it afterwards throws IllegalThreadStateException. Threads inherit daemon status from the creating thread.

Thread Fundamentals · continued

Q8. What is thread priority and should you rely on it?

A hint between 1 and 10 (default 5) for the scheduler. Behaviour is platform dependent and priorities may be ignored, so correctness must never depend on them.

Q9. What is a thread scheduler?

The OS (and JVM) component that decides which runnable thread gets CPU time. Java gives no guarantee about order or fairness of scheduling.

Q10. What is context switching and why is it costly?

Saving one thread's CPU state and restoring another's. It costs CPU cycles and cache locality, so far more runnable threads than cores reduces throughput.

Q11. What are the advantages of multithreading?

Better CPU utilization, responsiveness (background work off the UI/request thread), higher throughput on multi-core machines, and a natural model for independent activities.

Q12. What are the main risks of multithreading?

Race conditions, visibility problems, deadlocks, starvation, higher complexity, harder debugging and non-reproducible failures.

↑ Contents8

Thread Fundamentals · continued

Q13. What are CPU-bound and I/O-bound tasks, and how do they affect thread counts?

CPU-bound tasks keep a core busy, so about one thread per core is ideal. I/O-bound tasks spend time waiting, so more threads (or virtual threads) can keep the CPU busy during waits.

Q14. How much memory does a platform thread use?

Each reserves a stack, commonly about 1 MB by default on 64-bit systems (set with -Xss), plus native bookkeeping. This limits how many platform threads you can create.

Q15. What is a thread-safe class?

One that preserves its invariants and behaves correctly when used by multiple threads without extra synchronization by callers. Thread safety can come from immutability, confinement, locking or atomics.

Q16. What is the difference between a user thread and a daemon thread in terms of JVM exit?

The JVM waits for all user threads to finish before exiting, but does not wait for daemon threads, which are stopped abruptly when the last user thread ends.

Creating and Starting Threads

KEY KNOWLEDGE

  • There are several ways to define work for a thread, and they differ mainly in whether they return results and in how much control you have over execution.
Runnable task = () -> System.out.println("running in " + Thread.currentThread().getName());
Thread t = new Thread(task, "worker-1");
t.start();            // new call stack, then run() is invoked
// t.run();           // WRONG: runs in the caller's thread

    Q17. What are the ways to create a thread in Java?

    Extend Thread, implement Runnable, implement Callable and submit to an executor, use a lambda/method reference as a Runnable, use CompletableFuture.supplyAsync, or create virtual threads with Thread.ofVirtual() (Java 21+).

    Q18. Why is implementing Runnable usually preferred over extending Thread?

    Java has single inheritance, so extending Thread consumes your only superclass. Runnable separates the task from the execution mechanism and works with thread pools.

    Q19. What is the difference between start() and run()?

    start() creates a new thread of execution which then calls run(). Calling run() directly is an ordinary method call in the current thread with no concurrency.

    ↑ Contents12

    Creating and Starting Threads · continued

    Q20. What happens if you call start() twice on the same Thread object?

    The second call throws IllegalThreadStateException. A thread can be started only once, even after it terminates.

    Q21. What is the difference between Runnable and Callable?

    Runnable.run() returns nothing and cannot throw checked exceptions. Callable.call() returns a value and may throw checked exceptions; it is used with executors and Future.

    Q22. How can a thread return a result?

    Use Callable with a Future, CompletableFuture, or publish the result into a thread-safe structure (for example a BlockingQueue or AtomicReference).

    Q23. What is FutureTask?

    A class that implements both Runnable and Future, wrapping a Callable. It can be run by a plain thread or an executor, and its result retrieved later.

    Q24. How do you name threads and why does it matter?

    Use the Thread(Runnable, String) constructor, setName(), or a custom ThreadFactory. Meaningful names make logs and thread dumps readable.

    13

    Creating and Starting Threads · continued

    Q25. What is a ThreadFactory?

    An interface with Thread newThread(Runnable r) that centralizes thread creation so you can set names, daemon flag, priority and uncaught exception handlers for pools.

    Q26. What is an UncaughtExceptionHandler?

    A callback invoked when a thread dies from an unhandled exception. Set it per thread or globally with Thread.setDefaultUncaughtExceptionHandler.

    Q27. What happens if a thread throws an unchecked exception?

    That thread terminates (after the handler runs). Other threads and the JVM continue, unless it was the last non-daemon thread.

    Q28. Can you override start()?

    Technically yes, but you must call super.start() or no thread is created. It is almost never a good idea.

    Q29. What is a ThreadGroup?

    A legacy way to organize threads into a hierarchy. It is rarely used today; executors and structured concurrency are preferred.

    Q30. How do you get the current thread and its identity?

    Thread.currentThread() returns the executing thread; threadId() (Java 19+) gives its unique id, replacing getId().

    Thread Lifecycle and Scheduling

    KEY KNOWLEDGE

    • A thread moves through the states of Thread.State: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING and TERMINATED. Java does not expose a separate RUNNING state; RUNNABLE covers both ready and executing threads.

    Q31. What are the states of a Java thread?

    NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING and TERMINATED, as defined by Thread.State.

    Q32. What is the NEW state?

    The thread object exists but start() has not been called, so no OS thread has been created yet.

    Q33. Is there a RUNNING state in Java?

    No. RUNNABLE means the thread is either executing or ready to execute, waiting only for CPU time.

    Q34. What causes the BLOCKED state?

    Waiting to enter a synchronized block or method whose monitor is held by another thread (or to re-enter after wait()).

    Q35. What causes the WAITING state?

    Waiting indefinitely for another thread: Object.wait() without timeout, Thread.join() without timeout, or LockSupport.park().

    ↑ Contents18

    Thread Lifecycle and Scheduling · continued

    Q36. What causes TIMED_WAITING?

    Waiting with a timeout: sleep(ms), wait(ms), join(ms), parkNanos, or timed lock/queue operations.

    Q37. What is the difference between BLOCKED and WAITING?

    BLOCKED is trying to acquire a monitor lock. WAITING has voluntarily given up and waits for an explicit signal, notification, or completion.

    Q38. How can you inspect a thread's state?

    Call thread.getState(), or take a thread dump with jstack or jcmd <pid> Thread.print to see all states.

    Q39. Can a terminated thread be restarted?

    No. Once TERMINATED, create a new Thread object. Pools avoid this by reusing worker threads for many tasks.

    Q40. What does isAlive() return?

    True if the thread has been started and has not yet terminated.

    Q41. What is preemptive scheduling versus time slicing?

    Preemptive scheduling lets the scheduler interrupt a running thread to run another. Time slicing gives each runnable thread a quantum in turn. Modern OSes combine both.

    Q42. What is thread starvation?

    A thread is repeatedly denied CPU time or a lock because others monopolize it, for example through unfair locks or priority abuse.

    19

    Thread Lifecycle and Scheduling · continued

    Q43. What is a spurious thread state transition worth knowing about?

    A thread can wake from wait() without being notified (a spurious wakeup), which is why waits must be in a loop that rechecks the condition.

    Q44. How does a thread move from WAITING back to RUNNABLE?

    Through notify()/notifyAll(), termination of the joined thread, LockSupport.unpark(), or an interrupt.

    Thread Control: sleep, join, yield, interrupt

    KEY KNOWLEDGE

    • Thread control methods let one thread coordinate with another. The key idea is cooperative cancellation: Java never safely kills a thread from outside, it asks the thread to stop through interruption.
    Thread worker = new Thread(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        try { doWork(); Thread.sleep(100); }
        catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // restore flag
            break;
        }
    }
});
worker.start();
worker.interrupt();   // request stop
worker.join();        // wait for completion

      Q45. What does Thread.sleep() do, and does it release locks?

      It pauses the current thread for the given time. It does not release any monitors the thread holds.

      Q46. What is the difference between sleep() and wait()?

      sleep() is a static Thread method and keeps locks. wait() belongs to Object, requires holding the monitor, releases it while waiting, and is woken by notify.

      ↑ Contents24

      Thread Control: sleep, join, yield, interrupt · continued

      Q47. What does join() do?

      It blocks the calling thread until the target thread terminates (or the optional timeout expires). It also establishes a happens-before edge.

      Q48. What does yield() do?

      It is a hint that the current thread is willing to give up its CPU slice. The scheduler may ignore it.

      Q49. What does interrupt() actually do?

      It sets the target thread's interrupt flag. If the thread is blocked in sleep, wait or join, it wakes with InterruptedException and the flag is cleared.

      Q50. What is the difference between interrupted() and isInterrupted()?

      Thread.interrupted() is static, tests the current thread and clears the flag. isInterrupted() is an instance method and does not clear the flag.

      Q51. How should InterruptedException be handled?

      Either propagate it, or restore the flag with Thread.currentThread().interrupt() and stop. Swallowing it silently breaks cancellation.

      25

      Thread Control: sleep, join, yield, interrupt · continued

      Q52. How do you stop a thread safely?

      Use cooperative cancellation: check the interrupt flag (or a volatile boolean) regularly, clean up and return. Request it with interrupt().

      Q53. Why are Thread.stop(), suspend() and resume() deprecated?

      stop() releases locks mid-update, leaving objects inconsistent. suspend() keeps locks while suspended and can cause deadlock. All are unsafe by design.

      Q54. Does interrupt() stop a thread blocked on I/O or lock acquisition?

      Not for plain blocking socket I/O or synchronized entry; those do not respond to interrupts. lockInterruptibly() and NIO interruptible channels do.

      Q55. Can you interrupt a thread that has not started?

      The call is allowed but has no effect on a NEW thread, since no execution exists yet. Interrupt status is not retained for a thread that has not started.

      Q56. What does join(timeout) guarantee?

      It waits at most the timeout, then returns even if the thread is still alive. You must check isAlive() afterwards if it matters.

      Q57. What does Thread.onSpinWait() do?

      A hint (Java 9+) that the caller is in a busy-wait loop, letting the CPU optimize power and pipeline use.

      ↑ Contents26

      Thread Control: sleep, join, yield, interrupt · continued

      Q58. Why should you not use sleep() to coordinate threads?

      Sleeping assumes timing that may not hold, creating flaky and slow code. Use latches, futures, conditions or blocking queues instead.

      Q59. What is a shutdown hook?

      A thread registered with Runtime.addShutdownHook() that runs when the JVM begins an orderly shutdown, used for cleanup.

      Q60. What is the happens-before effect of start() and join()?

      Actions before start() happen-before everything in the started thread, and everything in a thread happens-before a successful join() on it returns.

      Part 2 · Synchronization and Memory

      Synchronization and Intrinsic Locks

      KEY KNOWLEDGE

      • Synchronization provides mutual exclusion and memory visibility. Every Java object has an intrinsic lock (monitor). A synchronized method or block acquires that monitor; the lock is released automatically on exit, even when an exception is thrown.
      class Counter {
    private final Object lock = new Object();
    private int count;
    void increment() { synchronized (lock) { count++; } }
    int get()        { synchronized (lock) { return count; } }
}

        Q61. What is a race condition?

        A bug where the outcome depends on the timing of unsynchronized access to shared mutable state, such as check-then-act or read-modify-write sequences.

        Q62. What is a critical section?

        A block of code that accesses shared resources and must be executed by at most one thread at a time.

        Q63. What does the synchronized keyword guarantee?

        Mutual exclusion on the monitor, plus visibility: changes made before releasing a lock are visible to the next thread that acquires the same lock.

        ↑ Contents28

        Synchronization and Intrinsic Locks · continued

        Q64. What is the difference between a synchronized method and a synchronized block?

        A synchronized method locks this (or the Class object when static) for its whole body. A block locks a chosen object for only the critical lines, reducing contention.

        Q65. What lock does a static synchronized method use?

        The Class object (for example Foo.class), which is separate from any instance's lock.

        Q66. Can two threads run different synchronized instance methods of the same object at the same time?

        No. Both require the same monitor (this), so one waits. Different objects have different monitors.

        Q67. Can a static synchronized method and an instance synchronized method run concurrently?

        Yes, because they lock different objects: the Class object and the instance.

        Q68. Is synchronized reentrant?

        Yes. A thread holding a monitor can enter other synchronized code on the same object without blocking itself.

        Q69. What happens to the lock if an exception is thrown inside a synchronized block?

        The monitor is released automatically when control leaves the block.

        29

        Synchronization and Intrinsic Locks · continued

        Q70. Why use a private final lock object instead of this?

        Outside code could synchronize on your object and interfere or deadlock. A private lock keeps locking policy encapsulated.

        Q71. Why should you not synchronize on String literals, boxed values or class-wide shared objects?

        Interned strings and cached boxes are shared JVM-wide, so unrelated code may contend for the same lock.

        Q72. What happens if you synchronize on null?

        A NullPointerException is thrown.

        Q73. Can a constructor be synchronized?

        No, the modifier is not allowed. Use a synchronized block inside the constructor if necessary, and avoid letting this escape.

        Q74. Is i++ atomic?

        No. It is read, add and write. Use AtomicInteger, a lock, or LongAdder for concurrent counters.

        Q75. What is a compound action and why is it dangerous?

        A sequence like check-then-act or put-if-absent built from several individually safe calls. Without holding one lock across the whole sequence it is not atomic.

        ↑ Contents30

        Synchronization and Intrinsic Locks · continued

        Q76. What are lock elision and lock coarsening?

        JIT optimizations: elision removes locks on objects proven thread-confined; coarsening merges adjacent synchronized regions on the same lock.

        Q77. What is thread confinement?

        Keeping data accessible by only one thread (stack locals, ThreadLocal, single-thread executors), so no synchronization is needed.

        Q78. What is ThreadLocal and what is its main risk?

        It gives each thread its own copy of a variable. In pools, values can leak between tasks or cause memory leaks, so call remove() in a finally block.

        Memory Visibility, volatile and the Java Memory Model

        KEY KNOWLEDGE

        • Without synchronization, one thread may never see another thread's writes because of CPU caches and compiler reordering. The Java Memory Model (JMM) defines happens-before rules that guarantee visibility and ordering. volatile gives visibility and ordering for a single variable, but not atomic compound updates.

        Q79. What is the visibility problem?

        A write by one thread may not become visible to another thread without a proper happens-before relationship, so loops can spin forever on a stale value.

        Q80. What does volatile guarantee?

        Reads see the most recent write, and the access acts as a barrier against reordering. It does not make compound operations such as count++ atomic.

        Q81. When is volatile the right tool?

        For simple status flags, one-writer/many-reader values, and safe publication of immutable objects, where no atomic read-modify-write is needed.

        Q82. What is the difference between volatile and synchronized?

        Volatile is non-blocking visibility and ordering for one variable. Synchronized adds mutual exclusion for a whole block and also gives visibility.

        ↑ Contents32

        Memory Visibility, volatile and the Java Memory Model · continued

        Q83. What is the happens-before relationship?

        A JMM rule: if action A happens-before B, then A's effects are visible to B. Examples: unlock before later lock, volatile write before later read, start() before the thread's actions.

        Q84. What is instruction reordering?

        Compilers and CPUs may reorder independent instructions for speed. It is invisible within one thread but can be observed by others unless synchronized.

        Q85. What is a memory barrier?

        A low-level fence that prevents certain reorderings of memory operations. The JVM inserts barriers for volatile and synchronized.

        Q86. What is double-checked locking and why is volatile required?

        A lazy-initialization idiom that checks null before and inside a synchronized block. The field must be volatile, otherwise construction can be reordered and another thread may see a partially built object.

        Q87. What is safe publication?

        Making an object reference visible to other threads together with its fully constructed state, via volatile, final fields, locks, static initializers or concurrent collections.

        33

        Memory Visibility, volatile and the Java Memory Model · continued

        Q88. What do final fields guarantee in the JMM?

        After the constructor finishes, other threads see correctly initialized final fields without extra synchronization, provided this did not escape.

        Q89. What is this-escape?

        Letting the this reference leak from a constructor (for instance by starting a thread or registering a listener), so others may see a partly constructed object.

        Q90. Why are immutable objects automatically thread safe?

        Their state never changes after construction, so there is nothing to race on. Examples: String, LocalDate, records with immutable components.

        Q91. What is a data race versus a race condition?

        A data race is unsynchronized access where at least one access is a write. A race condition is a broader timing-dependent logic bug that can exist even without data races.

        Q92. What is the initialization-on-demand holder idiom?

        A private static nested class holds the singleton instance. Class initialization is lazy and thread safe, so no explicit locking is needed.

        Inter-Thread Communication

        KEY KNOWLEDGE

        • Threads coordinate by waiting for conditions and signalling changes. The classic low-level API is wait(), notify() and notifyAll() on an object's monitor. Higher-level tools such as BlockingQueue, Condition, latches and futures are safer and are preferred.
        synchronized (lock) {
    while (!conditionTrue) {      // always loop
        lock.wait();
    }
    // proceed
}
// other thread:
synchronized (lock) { conditionTrue = true; lock.notifyAll(); }

          Q93. What are wait(), notify() and notifyAll()?

          Methods on Object. wait() releases the monitor and suspends the thread; notify() wakes one waiter; notifyAll() wakes all waiters of that object.

          Q94. Why are they defined on Object rather than Thread?

          Because the monitor belongs to the object. Threads wait on and signal a specific object's monitor.

          Q95. Why must they be called from a synchronized context?

          The caller must own the monitor, otherwise IllegalMonitorStateException is thrown. It also prevents a race between checking a condition and waiting.

          ↑ Contents38

          Inter-Thread Communication · continued

          Q96. Why must wait() be called in a while loop?

          To recheck the condition after waking, because of spurious wakeups and because another thread may have changed state before this thread regained the lock.

          Q97. What is a lost wakeup?

          A notification sent before the other thread began waiting, leaving the waiter asleep forever. Guard with a condition variable checked under the lock.

          Q98. notify() or notifyAll()?

          notifyAll() is the safer default. notify() is only safe when all waiters are equivalent and one wake-up suffices.

          Q99. What is the producer-consumer problem?

          Producers add items to a bounded buffer and consumers remove them. Producers wait when the buffer is full and consumers wait when it is empty.

          Q100. How does BlockingQueue simplify producer-consumer?

          put() blocks when full and take() blocks when empty, so no manual wait/notify is required.

          Q101. What is the Condition interface?

          A replacement for wait/notify tied to a Lock, created via newCondition(). It supports multiple wait sets per lock, with await, signal and signalAll.

          39

          Inter-Thread Communication · continued

          Q102. What is an Exchanger?

          A rendezvous point where two threads swap objects with exchange().

          Q103. What is a Phaser?

          A reusable barrier with a dynamic number of parties and multiple phases, more flexible than CyclicBarrier.

          Q104. How can you make Thread B run after Thread A finishes?

          Call a.join() in B, use a CountDownLatch, or chain stages with CompletableFuture.thenRun.

          Part 3 · Liveness, Locks and Synchronizers

          Deadlock, Livelock and Starvation

          KEY KNOWLEDGE

          • Liveness problems occur when threads cannot make progress. Deadlock needs four conditions: mutual exclusion, hold and wait, no preemption and circular wait. Breaking any one of them prevents deadlock; the most practical fix is a global lock ordering.
          // Classic deadlock
Thread t1: synchronized (A) { synchronized (B) { ... } }
Thread t2: synchronized (B) { synchronized (A) { ... } }
// Fix: both threads always lock A before B.

            Q105. What is a deadlock?

            Two or more threads wait forever for locks held by each other, so none can proceed.

            Q106. What are the four necessary conditions for deadlock?

            Mutual exclusion, hold and wait, no preemption, and circular wait.

            Q107. How do you prevent deadlocks?

            Acquire locks in a consistent global order, hold them briefly, avoid calling unknown code under a lock, and use tryLock with timeouts or higher-level utilities.

            ↑ Contents44

            Deadlock, Livelock and Starvation · continued

            Q108. How do you detect a deadlock?

            Take a thread dump (jstack, jcmd Thread.print), which reports deadlocks, or use ThreadMXBean.findDeadlockedThreads() programmatically.

            Q109. What is a livelock?

            Threads keep responding to each other and stay active but make no progress, like two people repeatedly stepping aside in a corridor.

            Q110. What is starvation?

            A thread never gets the resource or CPU time it needs because others always win, often from unfair locks or priority misuse.

            Q111. What is priority inversion?

            A low-priority thread holding a lock delays a high-priority thread, especially when medium-priority threads preempt the lock holder.

            Q112. How can tryLock help avoid deadlock?

            It lets a thread give up and back off if it cannot acquire all needed locks, breaking the hold-and-wait condition.

            Q113. What is lock ordering?

            A rule that all threads acquire multiple locks in the same global order (for example by account id), eliminating circular wait.

            45

            Deadlock, Livelock and Starvation · continued

            Q114. What is thread contention and how do you reduce it?

            Many threads competing for one lock. Reduce with smaller critical sections, lock striping, read-write locks, atomics or lock-free structures.

            Q115. What is a thread dump and how do you read it?

            A snapshot of all thread states and stacks. Look for BLOCKED threads, lock owners, repeated identical stacks and the deadlock report.

            Q116. What is a spin lock and when is it appropriate?

            A lock where waiting threads loop checking the lock instead of sleeping. It is efficient only for extremely short critical sections.

            Explicit Locks and Synchronizers

            KEY KNOWLEDGE

            • java.util.concurrent.locks provides explicit locks with features that synchronized lacks: timed and interruptible acquisition, optional fairness, multiple conditions and read/write splitting. The price is manual unlocking, so always release in a finally block.
            private final ReentrantLock lock = new ReentrantLock();
void update() {
    lock.lock();
    try { /* critical section */ }
    finally { lock.unlock(); }
}

              Q117. What is the Lock interface?

              An explicit locking API with lock, unlock, tryLock, lockInterruptibly and newCondition, more flexible than synchronized.

              Q118. What is ReentrantLock?

              The standard Lock implementation. The owning thread may acquire it repeatedly and must unlock the same number of times.

              Q119. Why must unlock() be in a finally block?

              A Lock is not released automatically. If an exception skips unlock(), other threads block forever.

              ↑ Contents50

              Explicit Locks and Synchronizers · continued

              Q120. How does ReentrantLock differ from synchronized?

              It adds tryLock, timeouts, interruptible acquisition, fairness and multiple conditions, but needs manual unlock. synchronized is simpler and auto-releases.

              Q121. What is a fair lock?

              new ReentrantLock(true) grants the lock to the longest-waiting thread. It reduces starvation but lowers throughput.

              Q122. What is ReadWriteLock?

              A pair of locks: many readers may hold the read lock concurrently, but the write lock is exclusive. It suits read-heavy data.

              Q123. Can ReentrantReadWriteLock upgrade a read lock to a write lock?

              No, upgrading can deadlock. Downgrading is supported: acquire the read lock before releasing the write lock.

              Q124. What is StampedLock?

              A lock with write, read and optimistic read modes using stamps. It is not reentrant and has no conditions.

              Q125. What is an optimistic read?

              tryOptimisticRead() returns a stamp without locking; after reading, validate(stamp) confirms no write occurred, otherwise fall back to a real read lock.

              51

              Explicit Locks and Synchronizers · continued

              Q126. What is a Semaphore?

              A counter of permits. acquire() takes one (blocking if none) and release() returns one. It limits concurrent access to a resource.

              Q127. What is CountDownLatch?

              A one-shot barrier. Threads calling await() block until countDown() has been called enough times to reach zero.

              Q128. What is CyclicBarrier and how does it differ from CountDownLatch?

              A reusable barrier where a fixed set of threads wait for each other. A latch is single-use and the counting threads are not necessarily the waiting ones.

              Q129. Semaphore versus mutex?

              A mutex has one owner and is released by that owner. A semaphore has N permits and any thread can release, so it has no ownership.

              Q130. What is AbstractQueuedSynchronizer?

              The framework behind ReentrantLock, Semaphore, CountDownLatch and more, built on a volatile state integer and a FIFO queue of waiters.

              Q131. What are LockSupport.park() and unpark()?

              Low-level primitives that block and unblock threads. Permit semantics mean an unpark before park is not lost.

              Explicit Locks and Synchronizers · continued

              Q132. What does lockInterruptibly() provide?

              Lock acquisition that can be aborted by interrupting the waiting thread, which then receives InterruptedException.

              Part 4 · The Executor Framework

              Executor Framework Core

              KEY KNOWLEDGE

              • The Executor framework decouples task submission from task execution. You describe work as Runnable or Callable tasks and hand them to an ExecutorService, which owns thread creation, reuse, queuing and lifecycle. This avoids the cost and risk of creating raw threads per task.
              ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Integer> f = pool.submit(() -> compute());
Integer result = f.get();      // blocks until done
pool.shutdown();
              • Interface hierarchy: Executor (execute) → ExecutorService (lifecycle, submit, invokeAll) → ScheduledExecutorService (delayed and periodic tasks). ThreadPoolExecutor and ForkJoinPool are the main implementations.

              Q133. What is the Executor framework?

              A set of interfaces and classes in java.util.concurrent that separate task submission from execution policy (threading, queuing, scheduling).

              Q134. What is the difference between Executor, ExecutorService and ScheduledExecutorService?

              Executor only has execute(Runnable). ExecutorService adds lifecycle control and submit/invokeAll. ScheduledExecutorService adds delayed and periodic execution.

              ↑ Contents56

              Executor Framework Core · continued

              Q135. What is the Executors class?

              A utility class with factory methods that create common executors, such as fixed, cached, single-thread, scheduled and work-stealing pools.

              Q136. Why use a thread pool instead of creating threads per task?

              It reuses threads to avoid creation cost, bounds resource usage, queues excess work, and provides lifecycle and monitoring.

              Q137. What does newFixedThreadPool(n) create?

              A pool of n threads with an unbounded task queue. Extra tasks wait in the queue.

              Q138. What does newCachedThreadPool() create?

              A pool that creates threads on demand, reuses idle ones and removes threads idle for 60 seconds. It has no upper bound on thread count.

              Q139. What does newSingleThreadExecutor() guarantee?

              Tasks run sequentially in submission order on one worker, and a replacement worker is created if it dies.

              Q140. What does newScheduledThreadPool() do?

              Creates a pool that can run tasks after a delay or at fixed intervals.

              57

              Executor Framework Core · continued

              Q141. What does newWorkStealingPool() do?

              Creates a ForkJoinPool sized to the available processors, where idle workers steal tasks from busy ones.

              Q142. What does newVirtualThreadPerTaskExecutor() do?

              Java 21+ factory that starts a new virtual thread for every submitted task, with no pooling.

              Q143. What is the difference between execute() and submit()?

              execute(Runnable) returns nothing and exceptions go to the thread's handler. submit() returns a Future and captures exceptions inside it until get().

              Q144. What is the difference between shutdown() and shutdownNow()?

              shutdown() stops accepting tasks but runs queued ones. shutdownNow() interrupts running tasks and returns the list of tasks never started.

              Q145. How do you shut down an ExecutorService correctly?

              Call shutdown(), wait with awaitTermination(timeout), and if it times out call shutdownNow(). From Java 19, close() (try-with-resources) does this.

              Q146. What happens if you forget to shut down an executor?

              Non-daemon worker threads keep the JVM alive and leak resources, so the application may never exit.

              ↑ Contents58

              Executor Framework Core · continued

              Q147. What do invokeAll() and invokeAny() do?

              invokeAll runs a collection of Callables and returns all futures when complete. invokeAny returns one successful result and cancels the rest.

              Q148. What is a CompletionService?

              A wrapper that returns futures in completion order via take() or poll(), so you can process results as they finish.

              ThreadPoolExecutor Deep Dive

              KEY KNOWLEDGE

              • ThreadPoolExecutor is the configurable engine behind most pools. Its behaviour is defined by core size, maximum size, work queue, keep-alive time, thread factory and rejection handler. Understanding how tasks flow between these parts is a very common interview topic.
              ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4, 8,                               // core, max
    60, TimeUnit.SECONDS,               // keep-alive for extra threads
    new ArrayBlockingQueue<>(100),      // bounded queue
    new CustomThreadFactory("orders"),
    new ThreadPoolExecutor.CallerRunsPolicy());

                Q149. What are the constructor parameters of ThreadPoolExecutor?

                corePoolSize, maximumPoolSize, keepAliveTime with unit, a BlockingQueue, a ThreadFactory and a RejectedExecutionHandler.

                Q150. How does ThreadPoolExecutor handle a newly submitted task?

                If fewer than core threads exist, start a new thread. Else queue the task. If the queue is full and threads are below maximum, start a new thread. Otherwise invoke the rejection handler.

                Q151. Why do threads beyond core size only appear when the queue is full?

                The pool prefers queuing over growing. With an unbounded queue the maximum size is therefore never used.

                ↑ Contents62

                ThreadPoolExecutor Deep Dive · continued

                Q152. What are the rejection policies?

                AbortPolicy (throws RejectedExecutionException, default), CallerRunsPolicy (caller runs the task), DiscardPolicy (drops silently), DiscardOldestPolicy (drops oldest queued task), or a custom handler.

                Q153. What is CallerRunsPolicy good for?

                It slows producers down when the pool is saturated, because the submitting thread executes the task itself, providing natural back-pressure.

                Q154. Which queue types are used with thread pools?

                LinkedBlockingQueue (unbounded by default), ArrayBlockingQueue (bounded), SynchronousQueue (direct handoff) and PriorityBlockingQueue.

                Q155. How does a SynchronousQueue change pool behaviour?

                It has no capacity, so each task needs an available thread; otherwise the pool creates a new one up to the maximum. This is what cached pools use.

                Q156. Why are Executors factory methods discouraged in production?

                Fixed and single pools use unbounded queues (risking out-of-memory) and cached pools can create unbounded threads. Configure ThreadPoolExecutor directly with bounds.

                63

                ThreadPoolExecutor Deep Dive · continued

                Q157. How do you size a thread pool?

                For CPU-bound work about the number of cores (+1). For I/O-bound work use cores x (1 + wait time / compute time). Always validate with load tests.

                Q158. What is keepAliveTime?

                How long idle threads above the core size wait before terminating. With allowCoreThreadTimeOut(true) it also applies to core threads.

                Q159. What does prestartAllCoreThreads() do?

                Starts all core threads immediately so they are ready before the first tasks arrive.

                Q160. How do you monitor a ThreadPoolExecutor?

                Use getPoolSize(), getActiveCount(), getQueue().size(), getCompletedTaskCount(), and override beforeExecute/afterExecute for metrics.

                Q161. What happens when a task throws an exception in a pool?

                With execute(), the worker dies, is replaced and the exception reaches the uncaught handler. With submit(), the exception is stored in the Future and thrown on get().

                Q162. What is thread pool starvation deadlock?

                Tasks in a pool wait for results of other tasks queued in the same pool, but all threads are occupied, so nothing ever runs. Use separate pools or avoid blocking waits.

                ↑ Contents64

                ThreadPoolExecutor Deep Dive · continued

                Q163. How can you customize threads created by a pool?

                Provide a ThreadFactory to set names, daemon status, priority and exception handlers.

                Q164. Can a pool's size be changed at runtime?

                Yes, setCorePoolSize and setMaximumPoolSize can be adjusted while running, which helps with dynamic tuning.

                Q165. What is afterExecute() useful for?

                A hook run after each task. It receives the throwable (if any), so it can log failures, including those hidden inside futures when handled carefully.

                Q166. What is the difference between a bounded and an unbounded queue?

                A bounded queue limits memory and provides back-pressure via rejection. An unbounded queue never rejects but can exhaust memory under overload.

                Future, Callable and CompletableFuture

                KEY KNOWLEDGE

                • A Future represents the pending result of an asynchronous task but only supports blocking retrieval. CompletableFuture (Java 8+) adds non-blocking composition: chaining, combining, error handling and manual completion.
                CompletableFuture<String> cf = CompletableFuture
    .supplyAsync(() -> fetchUser(id), ioExecutor)
    .thenApply(User::getName)
    .thenCombine(CompletableFuture.supplyAsync(() -> fetchRole(id), ioExecutor),
                 (name, role) -> name + ":" + role)
    .exceptionally(ex -> "unknown")
    .orTimeout(2, TimeUnit.SECONDS);

                  Q167. What is a Future and which methods does it offer?

                  A handle to an asynchronous result with get(), get(timeout), cancel(), isDone() and isCancelled().

                  Q168. What exceptions can Future.get() throw?

                  InterruptedException, ExecutionException (wrapping the task's failure), CancellationException and TimeoutException for the timed version.

                  Q169. What are the limitations of Future?

                  Blocking retrieval, no callbacks, no composition, no manual completion and limited error handling.

                  ↑ Contents68

                  Future, Callable and CompletableFuture · continued

                  Q170. How do you cancel a task?

                  future.cancel(true) marks it cancelled and interrupts the running thread. The task must respond to interruption to stop promptly.

                  Q171. What is CompletableFuture?

                  A Future and CompletionStage that supports non-blocking callbacks, pipelines, combining and manual completion.

                  Q172. How do you create a CompletableFuture?

                  supplyAsync(supplier), runAsync(runnable), completedFuture(value), or new CompletableFuture<>() completed later with complete().

                  Q173. What is the difference between thenApply, thenAccept and thenRun?

                  thenApply transforms the result, thenAccept consumes it, and thenRun runs an action ignoring the result.

                  Q174. thenApply versus thenCompose?

                  thenApply maps a value to a value (like map). thenCompose maps to another CompletableFuture and flattens it (like flatMap).

                  Q175. How do you combine two independent futures?

                  thenCombine(other, biFunction) for two, and allOf or anyOf for many.

                  69

                  Future, Callable and CompletableFuture · continued

                  Q176. What is the difference between allOf and anyOf?

                  allOf completes when all futures complete (returns Void). anyOf completes when the first completes, with its result.

                  Q177. How do you handle errors in CompletableFuture?

                  exceptionally to recover, handle to process result or error, and whenComplete for side effects without changing the outcome.

                  Q178. join() versus get() on CompletableFuture?

                  get() throws checked exceptions. join() throws the unchecked CompletionException, which is convenient inside lambdas.

                  Q179. Why pass a custom executor to async methods?

                  By default they use the shared ForkJoinPool.commonPool(). Blocking I/O there can starve other users, so supply a dedicated pool.

                  Q180. How do you add a timeout to a CompletableFuture?

                  orTimeout(time, unit) fails with TimeoutException, and completeOnTimeout(value, time, unit) completes with a default (Java 9+).

                  Scheduled Executors and Fork/Join

                  KEY KNOWLEDGE

                  • ScheduledExecutorService runs tasks after a delay or repeatedly. ForkJoinPool is built for recursive divide-and-conquer work and uses work stealing so idle threads help busy ones. Parallel streams and many CompletableFuture async methods use the common ForkJoinPool.
                  ScheduledExecutorService ses = Executors.newScheduledThreadPool(2);
ses.scheduleAtFixedRate(() -> poll(), 0, 5, TimeUnit.SECONDS);

                    Q181. What are the scheduling methods of ScheduledExecutorService?

                    schedule (one-shot delay), scheduleAtFixedRate and scheduleWithFixedDelay (periodic).

                    Q182. scheduleAtFixedRate versus scheduleWithFixedDelay?

                    Fixed rate measures intervals from start to start. Fixed delay waits the given time after each run finishes.

                    Q183. What happens if a periodic task throws an exception?

                    Subsequent executions are suppressed and the task silently stops. Wrap the body in try-catch to keep it running.

                    Q184. Why prefer ScheduledExecutorService over Timer?

                    Timer uses one thread and dies if a task throws. The executor supports pools, better error handling and is not affected by system clock changes.

                    ↑ Contents74

                    Scheduled Executors and Fork/Join · continued

                    Q185. What is ForkJoinPool?

                    A pool for divide-and-conquer tasks that uses work stealing to keep all workers busy.

                    Q186. What is work stealing?

                    Each worker has its own deque of tasks; idle workers steal tasks from the tail of others' deques to balance load.

                    Q187. RecursiveTask versus RecursiveAction?

                    Both extend ForkJoinTask and implement compute(). RecursiveTask<V> returns a result; RecursiveAction does not.

                    Q188. What is the typical fork/join pattern?

                    If the task is small compute directly; else split it, fork() one part, compute() the other and join() the results.

                    Q189. What is the common pool and why can it be risky?

                    ForkJoinPool.commonPool() is shared by parallel streams and default async methods. Blocking or slow tasks there can slow unrelated code.

                    Q190. What is ManagedBlocker?

                    A ForkJoinPool mechanism that lets a task declare it may block so the pool can add a compensating thread.

                    Part 5 · Modern Java and Practice

                    Virtual Threads, Best Practices and Scenarios

                    KEY KNOWLEDGE

                    • Virtual threads (final in Java 21) are lightweight threads scheduled by the JVM on a small set of carrier threads. They make the simple thread-per-request style scalable for blocking I/O work. Use them for I/O-bound tasks, do not pool them, and avoid pinning from long blocking calls inside synchronized on older JDKs.
                    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> callRemoteService());
    }
} // close() waits for all tasks

                      Q191. What are virtual threads?

                      JVM-managed lightweight threads (Java 21+) that unmount from their carrier thread when they block, allowing millions of concurrent blocking tasks.

                      Q192. Platform thread versus virtual thread?

                      A platform thread maps 1:1 to an OS thread with a large fixed stack. A virtual thread is scheduled by the JVM, has a small growable stack and is cheap to create.

                      ↑ Contents78

                      Virtual Threads, Best Practices and Scenarios · continued

                      Q193. When should you use virtual threads?

                      For high numbers of blocking, I/O-bound tasks such as request handling and remote calls. They do not speed up CPU-bound work.

                      Q194. Why should virtual threads not be pooled?

                      They are cheap, so you create one per task. Pooling defeats the purpose and limits concurrency artificially; use a semaphore if you must limit access to a resource.

                      Q195. What is pinning?

                      A virtual thread stuck to its carrier while blocked inside a synchronized block or native call, reducing scalability. ReentrantLock avoids this in many cases.

                      Q196. What is structured concurrency?

                      Treating a group of related tasks as one unit with a clear lifetime so failures and cancellation propagate and no threads leak. The API has been in preview in recent JDK releases, so check your version.

                      Q197. What are best practices for writing multithreaded code?

                      Prefer immutability and confinement, use executors and concurrent collections instead of raw threads, keep locks short, order locks, release in finally, handle interrupts, name threads and shut down pools.

                      79

                      Virtual Threads, Best Practices and Scenarios · continued

                      Q198. How would you run N tasks in parallel and wait for all to finish?

                      Submit them to an ExecutorService and use invokeAll, or use a CountDownLatch, or CompletableFuture.allOf.

                      Q199. How would you implement a thread-safe counter?

                      Use AtomicInteger/LongAdder, or synchronize the increment, or guard with a lock. Plain or merely volatile ints are not safe.

                      Q200. How do you test concurrent code?

                      Use stress tests with many threads, latches to force interleavings, timeouts, tools such as jcstress, and review happens-before correctness. Avoid Thread.sleep in tests.
