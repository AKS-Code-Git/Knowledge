Part 1 · Foundations

Map Interface Basics and Core API

WHAT IS A MAP?

  • java.util.Map<K,V> stores key-value pairs. Keys are unique; each key maps to at most one value.
  • Map does NOT extend Collection or Iterable; it is a separate root of the Collections Framework. Use keySet(), values() or entrySet() to get Collection views.
  • Implementations differ in ordering, null support, thread safety and performance.

CORE METHODS

  • put, get, remove, containsKey, containsValue, size, isEmpty, clear, putAll.
  • Views: keySet(), values(), entrySet(). Nested interface: Map.Entry<K,V>.
  • Java 8 defaults: getOrDefault, putIfAbsent, computeIfAbsent, computeIfPresent, compute, merge, forEach, replaceAll, replace, remove(key,value).
  • Java 9+ factories: Map.of, Map.ofEntries, Map.entry; Java 10: Map.copyOf.

Q1. What is the Map interface in Java and how does it differ from Collection?

Map (java.util.Map<K,V>) holds unique keys mapped to values. It does not extend Collection, because Collection models a group of single elements while Map models associations. Collection operations like add(E) do not fit a key-value structure.

Q2. Why does Map not extend the Collection interface?

A Map is a mapping, not a group of elements, so add(E) and Iterator<E> have no natural meaning. Map instead exposes Collection views (keySet, values, entrySet) that bridge to Collection-based APIs.

Q3. List the main methods of the Map interface.

put, get, remove, containsKey, containsValue, size, isEmpty, clear, putAll, keySet, values, entrySet, plus Java 8 defaults such as getOrDefault, putIfAbsent, compute*, merge, forEach and replaceAll.

Map Interface Basics and Core API · continued

Q4. What does put(K,V) return?

The previous value associated with the key, or null if there was none (or if the key was previously mapped to null). Use containsKey to distinguish the two cases.

Q5. What does get(Object) return when the key is absent?

null. With maps that allow null values, null is ambiguous, so use containsKey or getOrDefault. Some maps (ConcurrentHashMap, Hashtable) never allow null values, which avoids the ambiguity.

Q6. What is the difference between get and getOrDefault?

getOrDefault(key, def) returns def only when the key is not mapped (for most implementations), without storing it. It avoids null checks, but it does not insert the default into the map.

Q7. What is the difference between put and putIfAbsent?

put always overwrites. putIfAbsent stores the value only if the key is absent (or mapped to null) and returns the existing value, or null if it inserted.

Q8. What is Map.Entry and how do you use it?

A nested interface representing one key-value pair, with getKey(), getValue() and setValue(). It is the element type of entrySet() and the efficient way to iterate keys and values together.

for (Map.Entry<String,Integer> e : map.entrySet()) {
    System.out.println(e.getKey() + "=" + e.getValue());
}

Q9. What are the different ways to iterate over a Map?

Iterate entrySet() (best when both key and value are needed), keySet(), values(), use map.forEach((k,v)->...), an explicit Iterator over entrySet() (needed for safe removal), or a stream of entrySet().

Q10. Why is iterating entrySet() preferred over keySet() plus get()?

keySet() plus get(k) performs an extra lookup per key (O(1) average for HashMap, O(log n) for TreeMap). entrySet() hands over key and value in one step.

Q11. What is the difference between keySet(), values() and entrySet()?

keySet() returns a Set<K>, values() returns a Collection<V> (duplicates allowed) and entrySet() returns a Set<Map.Entry<K,V>>. All three are live views backed by the map.

Q12. Are keySet() and values() copies or views?

Views. Removing from them removes the mapping from the map, and changes to the map are reflected in them. They generally do not support add, which throws UnsupportedOperationException.

Q13. What are the main implementations of Map and when do you use each?

HashMap (general purpose, unordered), LinkedHashMap (insertion or access order), TreeMap (sorted), Hashtable (legacy, synchronized), ConcurrentHashMap (concurrent), EnumMap (enum keys), WeakHashMap, IdentityHashMap and immutable maps from Map.of.

Q14. Can a Map contain duplicate keys or duplicate values?

Duplicate keys are not allowed (a later put replaces the earlier value). Duplicate values are allowed, since two different keys may map to equal values.

Complete Map Hierarchy

INTERFACE HIERARCHY

  • Map → SortedMap → NavigableMap → (TreeMap, via AbstractMap).
  • Map → ConcurrentMap → ConcurrentNavigableMap (also extends NavigableMap) → ConcurrentSkipListMap.
  • Java 21: SequencedMap extends Map; SortedMap extends SequencedMap; LinkedHashMap implements SequencedMap.
  • Map.Entry is a nested interface; AbstractMap.SimpleEntry and SimpleImmutableEntry are ready-made entries.

Q15. Draw the Map hierarchy in words. Which interfaces extend Map?

Directly: SortedMap, ConcurrentMap and (Java 21) SequencedMap. NavigableMap extends SortedMap, and ConcurrentNavigableMap extends both ConcurrentMap and NavigableMap.

Complete Map Hierarchy · continued

Q16. What is AbstractMap and why does it exist?

A skeletal implementation of Map. It implements most methods in terms of entrySet(), so a concrete map only needs to supply entrySet() (and put for a modifiable map). HashMap, TreeMap, EnumMap and others extend it.

Q17. What is the relationship between HashMap and LinkedHashMap?

LinkedHashMap extends HashMap and adds a doubly linked list through all entries, which preserves insertion order (or access order). It reuses the hash table for lookups.

Q18. What is the relationship between Hashtable and Properties?

Properties extends Hashtable<Object,Object>, so it inherits synchronization and null-hostility. It is meant for String keys and values (config files) and adds getProperty, setProperty, load and store.

Q19. What is the Dictionary class?

An obsolete abstract class (pre-Java 1.2) that Hashtable extends. It is superseded by the Map interface and should not be used in new code.

Q20. Which Map implementations are sorted?

TreeMap and ConcurrentSkipListMap, both implementing NavigableMap/SortedMap. Ordering comes from natural ordering of keys or a supplied Comparator.

Q21. Which Map implementations preserve insertion order?

LinkedHashMap. Immutable Map.of maps do not guarantee order, and HashMap has no ordering guarantee even if it appears stable in small tests.

Q22. What is SequencedMap (Java 21)?

An interface for maps with a defined encounter order. It adds firstEntry, lastEntry, pollFirstEntry, pollLastEntry, putFirst, putLast, reversed, sequencedKeySet, sequencedValues and sequencedEntrySet.

Q23. Which classes implement SequencedMap?

LinkedHashMap directly, and TreeMap and ConcurrentSkipListMap through SortedMap/NavigableMap, which extend SequencedMap in Java 21.

Q24. What is ConcurrentMap?

A Map with atomic operations for concurrent use: putIfAbsent, remove(key,value), replace(key,old,new) and atomic compute/merge semantics. ConcurrentHashMap is the standard implementation.

Q25. What is ConcurrentNavigableMap?

A ConcurrentMap that is also a NavigableMap, supporting concurrent sorted access and range views. The only JDK implementation is ConcurrentSkipListMap.

Q26. Which Map implementations are not part of AbstractMap?

Hashtable (extends Dictionary) and the immutable collection maps returned by Map.of, which extend AbstractImmutableMap internally. Third-party maps may implement Map directly.

Part 2 · Hash-Based Maps

HashMap Internals

HOW HASHMAP WORKS

  • Backed by an array of buckets (Node<K,V>[] table), created lazily on first put. Default capacity 16, load factor 0.75, threshold = capacity × load factor.
  • Index = (n - 1) & hash, where hash = h ^ (h >>> 16) spreads high bits into low bits. Capacity is always a power of two.
  • Collisions form a linked list per bucket. Since Java 8, a bin with 8+ nodes becomes a red-black tree if table capacity is at least 64 (TREEIFY_THRESHOLD=8, MIN_TREEIFY_CAPACITY=64); it untreeifies at 6.
  • Resize doubles the table when size exceeds the threshold; each bin splits into a low and a high list without recomputing hashes.

KEY FACTS

  • Average O(1) for get/put; worst case O(log n) with treeified bins (O(n) before Java 8).
  • Allows one null key and many null values. Not thread-safe. Iteration order is unspecified.

Q27. How does HashMap work internally?

It computes hashCode() of the key, spreads it with h ^ (h>>>16), picks bucket (n-1)&hash, and stores a Node there. On collision it chains nodes (list or tree) and uses equals() to find the exact key. get repeats the same steps.

Q28. What are the default initial capacity and load factor of HashMap?

Capacity 16 and load factor 0.75. The table is created lazily on the first insertion, and the first resize happens when size exceeds 12.

Q29. What is the load factor and what is the trade-off?

It is the fullness ratio that triggers resizing. A higher value saves memory but increases collisions and lookup time; a lower value reduces collisions but wastes memory and causes more resizes. 0.75 is a good balance.

HashMap Internals · continued

Q30. Why is HashMap capacity always a power of two?

So the bucket index can be computed with a fast bitmask (n-1) & hash instead of modulo, and so resizing can split buckets cleanly into low and high halves. new HashMap<>(10) is rounded up to 16.

Q31. What is the hash spreading function h ^ (h >>> 16)?

It XORs the upper 16 bits of the hashCode into the lower 16 bits. Because the index uses only the low bits of a small table, this reduces collisions for hash codes that differ only in high bits.

Q32. What happens when two keys have the same hashCode?

They land in the same bucket and are chained. HashMap compares hash first, then == or equals(), to identify an identical key; otherwise it appends a new node to the chain or tree.

Q33. What is treeification in Java 8 and when does it happen?

When a single bucket reaches 8 nodes and the table has at least 64 buckets, the linked list is converted into a red-black tree. If the table is smaller than 64, it resizes instead. It reverts to a list when a bin shrinks to 6 or fewer.

Q34. Why are the treeify and untreeify thresholds 8 and 6, not the same value?

The gap prevents thrashing: if both were 8, a bin hovering around that size would keep converting back and forth. With hashCodes spread well, 8 collisions in a bucket is statistically very rare (Poisson distribution).

Q35. What is the time complexity of HashMap operations?

get, put, remove and containsKey are O(1) on average; worst case O(log n) with treeified bins when keys are Comparable (O(n) for lists or non-comparable keys). containsValue is O(n).

HashMap Internals · continued

Q36. What is the contract between equals() and hashCode() for HashMap keys?

Equal objects must return equal hash codes. Unequal objects may share a hash, but good distribution is important. Violating the contract makes lookups fail even though the key appears present.

Q37. What happens if you use a mutable object as a key and change it after insertion?

Its hashCode may change, so the entry sits in the wrong bucket and get returns null; the entry becomes effectively unreachable and leaks. Prefer immutable keys such as String, Integer and records.

Q38. Does HashMap allow null keys and values?

Yes, one null key (always in bucket 0, hash 0) and any number of null values. HashMap.get(null) works, unlike in Hashtable or ConcurrentHashMap.

Q39. Is HashMap thread-safe? What can go wrong?

No. Concurrent writes can lose updates, corrupt size, or yield stale reads. In Java 7, concurrent resize could create a cyclic list and cause an infinite loop; Java 8 fixed that specific loop but not data races.

Q40. Why did Java 8 change resizing from head insertion to tail insertion?

Java 7 reversed bucket order on resize (head insertion), which enabled circular links under concurrency. Java 8 preserves relative order using low/high lists (tail insertion), removing that infinite-loop hazard.

Q41. How does rehashing (resize) work in Java 8?

A new table of double size is allocated; each node goes either to the same index or to index + oldCapacity, determined by one extra bit of its hash. Nodes are split into low and high lists without recalculating hashes.

HashMap Internals · continued

Q42. How can you avoid rehashing when the size is known?

Pre-size the map: capacity = expected / 0.75 + 1, or use HashMap.newHashMap(n) (Java 19+), which computes the right capacity. This avoids repeated resizing during bulk loads.

Q43. What is the difference between HashMap(int) capacity and the number of entries it can hold?

The argument is the table capacity (rounded to a power of two), not the entry count. A map of capacity 16 resizes after 12 entries, so new HashMap<>(100) does not hold 100 entries without resizing.

Q44. How does HashMap.get() work step by step?

Hash the key, compute the index, check the first node (hash and equals), then if it is a tree walk the tree, else walk the linked list comparing hash and equals. Return the value or null.

Q45. What is the HashDoS attack and how does Java 8+ mitigate it?

An attacker supplies many keys with colliding hashes, degrading a bucket to O(n). Treeification gives O(log n) per bucket for Comparable keys, and String hashing is cached; for stronger protection use a keyed or randomized structure.

Q46. How is HashMap.hashCode() and equals() defined?

Two maps are equal if they have the same mappings (same size and each entry equal). The hashCode is the sum of the hashCodes of its entries, where an entry's hashCode is key.hashCode() ^ value.hashCode().

Q47. How does HashMap.clone() behave?

It produces a shallow copy: a new table and entries, but the keys and values themselves are shared. Mutable values shared between copies can lead to surprising aliasing.

Q48. Why is String a popular key in HashMap?

String is immutable, caches its hashCode and has a well-defined equals(). This makes hashing cheap and safe against key mutation.

Part 2 · Hash-Based Maps

LinkedHashMap

KEY IDEAS

  • Extends HashMap and maintains a doubly linked list of entries (before/after), so iteration follows a predictable order.
  • Default: insertion order; re-inserting an existing key does not change its position.
  • new LinkedHashMap<>(cap, lf, true) enables access order: get/put moves the entry to the end. Combined with removeEldestEntry it forms an LRU cache.
  • Java 21: implements SequencedMap (firstEntry, lastEntry, putFirst, putLast, reversed).

Q49. What is LinkedHashMap and how is it different from HashMap?

It is a HashMap with a doubly linked list threaded through its entries, giving predictable iteration order (insertion or access order). It is slightly slower and uses more memory than HashMap.

Q50. How does LinkedHashMap maintain order internally?

Each entry extends HashMap.Node with before and after pointers. The map holds head and tail references, and hooks (afterNodeInsertion, afterNodeAccess, afterNodeRemoval) keep the list updated.

Q51. What is access-order mode in LinkedHashMap?

Constructed with accessOrder=true, each get or put of an existing key moves that entry to the end of the list. Iteration then goes from least recently accessed to most recently accessed.

Q52. How do you implement an LRU cache with LinkedHashMap?

Use access order and override removeEldestEntry to evict when the size exceeds a limit.

class LRU<K,V> extends LinkedHashMap<K,V> {
    private final int max;
    LRU(int max){ super(16, 0.75f, true); this.max = max; }
    @Override protected boolean removeEldestEntry(Map.Entry<K,V> e){
        return size() > max;
    }
}

LinkedHashMap · continued

Q53. What does removeEldestEntry do and when is it called?

It is a protected hook invoked after every put or putIfAbsent/computeIfAbsent insertion. Returning true removes the eldest (head) entry. By default it returns false.

Q54. Does re-inserting an existing key change insertion order in LinkedHashMap?

No, in insertion-order mode the original position is kept. In access-order mode the entry moves to the end because the put counts as an access.

Q55. What is the time complexity of LinkedHashMap operations?

Same as HashMap, O(1) average for get/put/remove. Iteration is O(size) rather than O(capacity + size), which makes iteration faster for sparse tables.

Q56. Is LinkedHashMap thread-safe? How can you make it so?

No. Wrap with Collections.synchronizedMap(...); for access-order maps even get mutates structure, so reads need the same lock. For concurrent LRU use a library such as Caffeine.

Q57. How do you reverse or access first/last entries of a LinkedHashMap in Java 21?

Use the SequencedMap methods: firstEntry(), lastEntry(), pollFirstEntry(), putLast(k,v) and reversed(). Before Java 21 you had to iterate the entry set to reach the last entry.

Q58. When would you choose LinkedHashMap over HashMap or TreeMap?

When you need predictable ordering (insertion or access) without paying the O(log n) cost of sorting, e.g., preserving JSON field order, caches with eviction, or building ordered report output.

Part 2 · Hash-Based Maps

Hashtable and Properties

HASHTABLE

  • Legacy class from Java 1.0, retrofitted to implement Map. Every public method is synchronized, which serializes all access.
  • No null keys or values (NPE). Default capacity 11, load factor 0.75, grows to 2n + 1. Index is (hash & 0x7FFFFFFF) % length.
  • Enumerators (keys(), elements()) are not fail-fast; iterators are. No treeification.

PROPERTIES

  • Properties extends Hashtable<Object,Object> for String config. Methods: getProperty(key[,default]), setProperty, load(Reader|InputStream), store, stringPropertyNames, loadFromXML.
  • A defaults Properties object can act as a fallback; get() ignores defaults but getProperty() consults them.

Q59. What is Hashtable and why is it considered legacy?

A synchronized hash table from Java 1.0. It locks the entire table on every operation, scales poorly, and is superseded by ConcurrentHashMap (concurrency) and HashMap (single thread).

Q60. What are the differences between HashMap and Hashtable?

Hashtable is synchronized, disallows null keys and values, extends Dictionary, has default capacity 11 and uses Enumeration as well as Iterator. HashMap is unsynchronized, allows nulls, and is faster.

Q61. Why does Hashtable not allow null keys or values?

It calls key.hashCode() and value.equals() directly, so null throws NullPointerException. The design also avoids ambiguity between a missing key and a null value in a synchronized API.

Q62. How does Hashtable compute the bucket index and grow?

(hash & 0x7FFFFFFF) % table.length, and when the threshold is exceeded it rehashes to oldCapacity * 2 + 1. Using a modulo of a non-power-of-two size is slower than HashMap's bitmask.

Hashtable and Properties · continued

Q63. Is Hashtable's iterator fail-fast?

Its iterator() (via entrySet/keySet) is fail-fast. The legacy Enumeration from keys() and elements() is not guaranteed to be fail-fast.

Q64. Is Hashtable completely thread-safe for compound operations?

Individual methods are atomic, but check-then-act sequences like if(!t.containsKey(k)) t.put(k,v) are not. Use putIfAbsent or external synchronization.

Q65. What is the Properties class and when do you use it?

A Hashtable subclass of String key-value pairs used for configuration files (.properties). It supports loading and storing from streams and readers, and default values.

Q66. What is the difference between Properties.get() and Properties.getProperty()?

get() is the Hashtable method that returns an Object and ignores defaults. getProperty() returns a String and falls back to the defaults Properties object, or to a supplied default value.

Q67. How do you load and save a properties file?

Use load(InputStream/Reader) to read key=value lines and store(OutputStream/Writer, comments) to write them. Prefer Reader/Writer with UTF-8, since the legacy byte-stream form assumes ISO-8859-1.

Properties p = new Properties();
try (Reader r = Files.newBufferedReader(Path.of("app.properties"))) {
    p.load(r);
}
String url = p.getProperty("db.url", "jdbc:h2:mem:");

Q68. Why is Properties considered a design flaw?

It inherits Hashtable's put(Object,Object), so non-String entries can be inserted, which break store. Its inheritance instead of composition is a classic example of a leaky design.

Q69. What are alternatives to Hashtable in modern Java?

ConcurrentHashMap for concurrent use, HashMap for single-threaded use, Collections.synchronizedMap when a synchronized wrapper over any map is needed, and Map.of for immutable data.

Q70. Does Collections.synchronizedMap equal Hashtable?

Similar locking (one mutex per map) but it wraps any Map, allows nulls if the backing map does, and you must manually synchronize on the map when iterating.

Part 3 · Sorted and Navigable Maps

SortedMap and NavigableMap

SORTEDMAP

  • Keeps keys in ascending order by natural ordering (Comparable) or a Comparator given at construction.
  • Methods: firstKey, lastKey, headMap(to), tailMap(from), subMap(from,to), comparator(). Range views are live; subMap is half-open [from, to).

NAVIGABLEMAP (JAVA 6)

  • Adds navigation: lowerKey/Entry, floorKey/Entry, ceilingKey/Entry, higherKey/Entry, firstEntry, lastEntry, pollFirstEntry, pollLastEntry.
  • Adds descendingMap, descendingKeySet, navigableKeySet and inclusive/exclusive range views: headMap(to, inclusive), tailMap(from, inclusive), subMap(from, fi, to, ti).

Q71. What is SortedMap and what guarantees does it give?

A Map whose keys are kept in ascending order, either by natural ordering or by a Comparator. Iteration of keySet, values and entrySet follows that order.

Q72. What is NavigableMap and how does it extend SortedMap?

It adds closest-match navigation (lower, floor, ceiling, higher), polling methods, descending views and range views with inclusive/exclusive bounds.

↑ Contents38

SortedMap and NavigableMap · continued

Q73. Explain lowerKey, floorKey, ceilingKey and higherKey.

lowerKey(k) is strictly less than k, floorKey(k) is less than or equal, ceilingKey(k) is greater than or equal, and higherKey(k) is strictly greater. Each returns null if no such key exists.

Q74. What is the difference between headMap, tailMap and subMap?

headMap(to) returns keys strictly less than to, tailMap(from) returns keys greater than or equal to from, and subMap(from,to) returns the range [from, to). NavigableMap overloads let you choose inclusivity.

Q75. Are the range views of SortedMap copies or live views?

Live views. Changes to the view write through to the backing map and vice versa. Inserting a key outside the view's range throws IllegalArgumentException.

Q76. How does a Comparator affect a SortedMap?

The Comparator defines both ordering and key equality (compare returns 0 means same key). It should be consistent with equals(), otherwise the map violates the general Map contract.

Q77. What is descendingMap()?

A reverse-order view of the map. firstKey() of the descending view is the last key of the original, and modifications write through.

Q78. What does pollFirstEntry() do?

Removes and returns the entry with the smallest key (or null if empty). It is useful for priority-queue-like patterns on a sorted map.

Q79. Is Map.Entry returned by firstEntry() modifiable?

No. Entries returned by NavigableMap navigation methods are snapshots and do not support setValue(); it throws UnsupportedOperationException.

Q80. Which implementations of NavigableMap exist in the JDK?

TreeMap and ConcurrentSkipListMap (through ConcurrentNavigableMap). Both are sorted; the second is thread-safe.

Part 3 · Sorted and Navigable Maps

TreeMap

TREEMAP INTERNALS

  • Implements NavigableMap using a self-balancing red-black tree (Entry nodes with left, right, parent and colour).
  • get, put, remove, containsKey are O(log n); iteration in sorted order is O(n). Not thread-safe.
  • No null key with natural ordering (NPE); null values are allowed. A custom Comparator may allow null keys if it handles them.
  • Key equality is decided by compareTo/compare, not equals().

Q81. How does TreeMap work internally?

It stores entries in a red-black tree ordered by key. Each insertion walks from the root comparing keys, links a new red node, then performs rotations and recolouring to keep the tree balanced.

Q82. What is a red-black tree and why does TreeMap use it?

A self-balancing binary search tree with colour rules that guarantee the longest path is at most twice the shortest, so operations are O(log n) in the worst case, with fewer rotations than AVL on insert/delete.

Q83. What is the time complexity of TreeMap operations?

O(log n) for put, get, remove, containsKey, floorKey and similar; O(n) for full iteration; containsValue is O(n). firstKey/lastKey are O(log n).

Q84. Does TreeMap allow null keys or null values?

Null values are allowed. A null key throws NullPointerException with natural ordering because compareTo is called on it; with a Comparator, null keys work only if the Comparator handles them.

Q85. How does TreeMap determine whether two keys are equal?

By comparison: compareTo() or compare() returning 0. It does not call equals() or hashCode(), so a Comparator inconsistent with equals can silently overwrite entries.

↑ Contents42

TreeMap · continued

Q86. What happens if TreeMap keys do not implement Comparable?

The first put throws ClassCastException, unless you supply a Comparator at construction (new TreeMap<>(comparator)).

Q87. How do you create a TreeMap with custom ordering?

Pass a Comparator: for example new TreeMap<>(Comparator.reverseOrder()) for descending keys or String.CASE_INSENSITIVE_ORDER for case-insensitive ordering.

TreeMap<String,Integer> m = new TreeMap<>(String.CASE_INSENSITIVE_ORDER);
m.put("Apple",1); m.put("apple",2);   // same key: size == 1

Q88. Can TreeMap be sorted by values?

Not directly, since it orders by key. To sort by value, copy entries into a list and sort with Map.Entry.comparingByValue(), or stream and collect into a LinkedHashMap.

Q89. What is the difference between HashMap and TreeMap?

HashMap is unordered, O(1) average, allows a null key and uses hashCode/equals. TreeMap is sorted, O(log n), forbids null keys (natural ordering) and uses compareTo/compare, and supports range and navigation queries.

Q90. Is TreeMap thread-safe? How do you make it so?

No. Wrap with Collections.synchronizedSortedMap or, for high concurrency, use ConcurrentSkipListMap. Iterators are fail-fast.

Q91. How do you get a sub-range of a TreeMap?

Use subMap, headMap or tailMap (live views) or the NavigableMap overloads with inclusive flags, for example map.subMap(10, true, 20, true).

Part 4 · Concurrent and Special-Purpose Maps

ConcurrentMap and ConcurrentHashMap

CONCURRENTHASHMAP (JAVA 8+)

  • Thread-safe hash map without a single global lock. Empty bins are filled with CAS; non-empty bins are updated while synchronizing on the bin's first node. Reads (get) are lock-free via volatile reads.
  • Java 7 used 16 Segment locks (concurrencyLevel); Java 8 replaced them with per-bin locking and treeified bins.
  • No null keys or values. Iterators are weakly consistent: never throw ConcurrentModificationException and may reflect some updates made after creation.
  • Size is tracked with striped counters (baseCount + CounterCell[]), like LongAdder; prefer mappingCount().

ATOMIC AND BULK OPERATIONS

  • Atomic: putIfAbsent, computeIfAbsent, compute, merge, replace, remove(k,v).
  • Bulk with a parallelism threshold: forEach, search, reduce; ConcurrentHashMap.newKeySet() makes a concurrent Set.

Q93. What is ConcurrentHashMap and why use it?

A highly concurrent hash map that allows many readers and writers at once with fine-grained locking, giving far better scalability than Hashtable or synchronizedMap.

Q94. How does ConcurrentHashMap achieve thread safety in Java 8?

It uses CAS to insert into empty bins, synchronized on the head node of a bin for updates in non-empty bins, and volatile fields for lock-free reads. Treeification and cooperative resizing are also supported.

Q95. How was ConcurrentHashMap implemented in Java 7?

As an array of Segments (each a ReentrantLock guarding a small hash table). Default concurrencyLevel was 16, so up to 16 threads could write concurrently.

↑ Contents48

ConcurrentMap and ConcurrentHashMap · continued

Q96. Why does ConcurrentHashMap not allow null keys or values?

A null from get would be ambiguous (absent or mapped to null), and in a concurrent setting containsKey followed by get cannot resolve it safely. Disallowing nulls keeps semantics unambiguous.

Q97. What does 'weakly consistent' iteration mean?

The iterator reflects the map state at or after its creation, never throws ConcurrentModificationException, and may or may not reflect later modifications. Each element is returned at most once.

Q98. What is the difference between ConcurrentHashMap and Collections.synchronizedMap?

The synchronized wrapper uses one mutex for all operations and needs manual locking for iteration. ConcurrentHashMap locks per bin, has lock-free reads, supports atomic compound methods and non-failing iterators.

Q99. What is the difference between ConcurrentHashMap and Hashtable?

Hashtable locks the whole table for every method. ConcurrentHashMap allows concurrent reads and fine-grained writes, so it scales. Both forbid null keys and values.

Q100. Is computeIfAbsent atomic in ConcurrentHashMap?

Yes. The mapping function runs at most once per key while the bin is locked, so keep it short and do not modify the map inside it (this can deadlock or throw IllegalStateException: Recursive update).

Q101. Does ConcurrentHashMap's get() use locks?

No. Reads are lock-free and rely on volatile semantics, which is why read-heavy workloads scale so well.

Q102. How do you implement a thread-safe counter map with ConcurrentHashMap?

Use merge (atomic) or LongAdder values for heavy contention.

ConcurrentHashMap<String,Integer> c = new ConcurrentHashMap<>();

// high contention:

Q103. Are compound actions like check-then-put safe with ConcurrentHashMap?

Not if written as separate calls (if(!m.containsKey(k)) m.put(k,v)). Use the atomic putIfAbsent, computeIfAbsent, compute or merge instead.

Q104. What is mappingCount() and how does it differ from size()?

mappingCount() returns a long and is preferred because a map can hold more than Integer.MAX_VALUE mappings. Both are estimates under concurrent updates.

Q105. What do the parallelismThreshold bulk methods do?

forEach, search, reduce and variants run in parallel using the common ForkJoinPool when the estimated map size exceeds the threshold. Long.MAX_VALUE forces sequential and 1 maximizes parallelism.

Q106. What is ConcurrentHashMap.newKeySet()?

A static factory that returns a concurrent Set<K> backed by a ConcurrentHashMap, a modern replacement for Collections.newSetFromMap(new ConcurrentHashMap<>()).

Q107. How does ConcurrentHashMap resize?

Resizing is cooperative: threads that see a resize in progress help transfer bins to the new table (ForwardingNode markers redirect readers), so growth does not block the whole map.

ConcurrentSkipListMap

KEY IDEAS

  • A concurrent, sorted, scalable ConcurrentNavigableMap built on a skip list: layered linked lists where higher levels skip over more nodes.
  • Lock-free using CAS. O(log n) expected for get/put/remove; size() is O(n) and not constant-time.
  • Sorted by natural ordering or a Comparator. No null keys or values. Iterators are weakly consistent.

Q109. What is ConcurrentSkipListMap?

A thread-safe sorted map based on a skip list, implementing ConcurrentNavigableMap. It is the concurrent counterpart of TreeMap.

Q110. What is a skip list and why is it good for concurrency?

A probabilistic multi-level linked list giving expected O(log n) search. Insertions touch only a few local pointers, so they can be implemented lock-free with CAS, unlike tree rebalancing which affects many nodes.

Q111. When should you use ConcurrentSkipListMap instead of a synchronized TreeMap?

When many threads read and write a sorted map concurrently, since it avoids a single lock and offers atomic navigation (floor, ceiling, pollFirstEntry). For single-threaded use, TreeMap is faster.

Q112. Why is size() O(n) in ConcurrentSkipListMap?

There is no shared counter to avoid contention; it traverses the bottom level to count elements, and the result may be stale under concurrent modification.

Q113. Does ConcurrentSkipListMap allow null keys or values?

No. Both keys and values must be non-null, consistent with the ConcurrentMap conventions.

WeakHashMap, IdentityHashMap and EnumMap

WEAKHASHMAP

  • Keys are held through WeakReference. When a key is no longer strongly reachable, the GC may reclaim it, and the entry is removed lazily (stale entries are expunged through a ReferenceQueue on access).
  • Values are strongly referenced, so a value that refers to its own key prevents removal. Not for String literals or cached boxed Integers (always strongly reachable).

IDENTITYHASHMAP

  • Compares keys with == and uses System.identityHashCode, ignoring equals/hashCode. Open addressing with linear probing in one array. Violates the general Map contract on purpose.

ENUMMAP

  • Keys are of one enum type; internally an array indexed by ordinal(). Iteration follows enum declaration order. No null keys; null values allowed. Very fast and compact.

Q115. What is WeakHashMap and when is it used?

A hash map whose keys are weakly referenced. Entries disappear after the key is garbage collected, which suits canonicalizing mappings and caches of metadata that should not keep their keys alive.

Q116. How does WeakHashMap remove stale entries?

Keys are wrapped in WeakReferences registered with a ReferenceQueue. After GC enqueues cleared references, methods such as size, get and put call expungeStaleEntries() to remove them.

Q117. Why can a WeakHashMap fail to release entries?

If the value strongly references the key (directly or indirectly), the key never becomes weakly reachable. Also, keys such as interned Strings, enum constants and cached Integers are always strongly reachable.

↑ Contents56

WeakHashMap, IdentityHashMap and EnumMap · continued

Q118. What is the difference between WeakHashMap and HashMap with SoftReference values?

WeakHashMap tracks the lifetime of keys using weak references (collected at the next GC once unreachable). Soft references are cleared only under memory pressure and suit memory-sensitive caches.

Q119. What is IdentityHashMap?

A Map that uses reference equality (==) for keys and values instead of equals(). It is used for topology-preserving object graph operations such as serialization or deep copy, where each object instance is distinct.

Q120. How does IdentityHashMap store entries differently from HashMap?

It has no Node objects: keys and values sit in alternating slots of one Object array, with linear probing for collisions. This uses less memory but has poorer behavior under heavy clustering.

Q121. Why does IdentityHashMap violate the Map contract?

Map specifies equals-based comparison, whereas IdentityHashMap compares references. Two equal Strings created with new String would be two distinct keys.

Q122. What is EnumMap and how is it implemented?

A specialized Map for enum keys, backed by an array of values indexed by the enum's ordinal. It gives O(1) operations without hashing and iterates in the order of enum constants.

Q123. Why prefer EnumMap over HashMap for enum keys?

It is faster, uses less memory, has no hash collisions and keeps natural enum ordering. The enum type must be supplied when constructing: new EnumMap<>(Day.class).

Q124. Does EnumMap allow null?

No null keys (NullPointerException); null values are allowed. Internally null values are masked with a sentinel object.

WeakHashMap, IdentityHashMap and EnumMap · continued

Q125. Is EnumMap thread-safe?

No. Wrap with Collections.synchronizedMap if needed. Its iterators are weakly consistent rather than fail-fast.

Q126. What is the EnumMap iteration order?

Natural order of the enum constants (declaration order), regardless of insertion order.

Q127. How does Collections.newSetFromMap relate to these maps?

It builds a Set from any empty Map, e.g. newSetFromMap(new WeakHashMap<>()) for a weak set or new IdentityHashMap<>() for an identity-based set.

Q128. Give a use case where IdentityHashMap is the right choice.

Tracking visited objects while traversing an object graph with cycles, where two distinct but equals() instances must be treated as separate.

Immutable and Unmodifiable Maps

OPTIONS

  • Map.of(k1,v1,...) supports up to 10 pairs; Map.ofEntries(Map.entry(k,v), ...) has no limit. Map.copyOf(map) makes an immutable copy (Java 10).
  • Immutable maps reject nulls (keys and values), duplicate keys (IllegalArgumentException) and all modification (UnsupportedOperationException). Iteration order is unspecified and varies between JVM runs.
  • Collections.unmodifiableMap(m) is only a read-only view: changes to the underlying map remain visible. Collections.emptyMap() and singletonMap() are immutable specials.
  • Stream.collect(Collectors.toUnmodifiableMap(...)) produces an unmodifiable map.

Q129. How do you create an immutable Map in Java 9+?

Use Map.of(k1,v1,k2,v2) for up to 10 entries, Map.ofEntries(Map.entry(...), ...) for more, or Map.copyOf(existing) to snapshot another map.

Q130. What is the difference between Collections.unmodifiableMap and Map.copyOf?

unmodifiableMap is a read-only view that still reflects changes made to the wrapped map. Map.copyOf creates an independent immutable snapshot with null-hostile and truly immutable semantics.

Q131. Does Map.of allow null keys or values?

No. Any null throws NullPointerException, and so does containsKey(null) or get(null) on those maps.

Q132. What happens when you pass duplicate keys to Map.of?

It throws IllegalArgumentException at creation time (in contrast to a builder that would silently overwrite).

Q133. Is the iteration order of Map.of stable?

No. The order is unspecified and deliberately randomized per JVM instance (a SALT), so code must not rely on it.

Immutable and Unmodifiable Maps · continued

Q134. Is an immutable map really immutable if its values are mutable?

The map structure cannot change, but mutable values (e.g., a List) can still be modified, so the content is only shallowly immutable. Use immutable values for deep immutability.

Q135. Why is Map.entry(k,v) useful?

It creates an immutable, null-hostile Map.Entry, for use with Map.ofEntries or in streams, and is easier than new AbstractMap.SimpleEntry<>(k,v).

Q136. What is Collections.emptyMap() vs Map.of()?

Both return an immutable empty map. Collections.emptyMap() is a serializable singleton from Java 1.5 that tolerates null queries, while Map.of() is the Java 9 collection factory.

Q137. How do you create an unmodifiable map from a stream?

Use Collectors.toUnmodifiableMap(keyFn, valueFn) (Java 10) or collect into a Map and wrap with Map.copyOf. Duplicate keys throw IllegalStateException.

Q138. How do you make a defensive copy of a map field in a class?

Copy on the way in and out: this.m = Map.copyOf(input) in the constructor and return the immutable field directly; for maps needing nulls use Collections.unmodifiableMap(new HashMap<>(input)).

Java 8+ Map API and Streams

DEFAULT METHODS

  • getOrDefault(k,d), putIfAbsent(k,v), computeIfAbsent(k,fn), computeIfPresent(k,bifn), compute(k,bifn), merge(k,v,bifn), replace, replaceAll(bifn), forEach(biconsumer), remove(k,v).
  • Returning null from compute*/merge functions removes the mapping.
  • Helpers: Map.Entry.comparingByKey(), comparingByValue(); Collectors.toMap, groupingBy, counting, partitioningBy.

Q139. What does computeIfAbsent do and when do you use it?

If the key is absent (or maps to null), it computes the value with the function, stores it and returns it. It is ideal for multi-value maps and caches: map.computeIfAbsent(k, x -> new ArrayList<>()).add(v).

Q140. What is the difference between compute, computeIfAbsent and computeIfPresent?

computeIfAbsent runs only if the key is absent; computeIfPresent only if present; compute always runs with the current value (maybe null). Returning null from compute* removes the entry.

Q141. How does merge() work?

merge(key, value, fn) stores value if the key is absent, otherwise stores fn(oldValue, value). If fn returns null, the mapping is removed. It is the idiom for counting.

Map<String,Integer> freq = new HashMap<>();
for (String w : words) freq.merge(w, 1, Integer::sum);

Q142. What is the difference between merge and compute?

merge combines an existing value with a supplied one and never passes null to the function. compute receives the key and the current value (null if absent) and has full control of the result.

Q143. What does replaceAll do?

Replaces every value with the result of a BiFunction applied to key and value, e.g. map.replaceAll((k,v) -> v * 2).

Q144. What is forEach on a Map and how does it differ from entrySet iteration?

map.forEach((k,v) -> ...) is an internal iteration taking a BiConsumer. It is concise but cannot remove entries safely or use break/continue.

Q145. How do you convert a Map to a stream and sort by value?

Stream the entrySet(), sort with Map.Entry.comparingByValue() and collect into a LinkedHashMap to preserve order.

Map<String,Integer> sorted = map.entrySet().stream()
  .sorted(Map.Entry.<String,Integer>comparingByValue().reversed())
  .collect(Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue,
           (a,b)->a, LinkedHashMap::new));

Q146. What happens with Collectors.toMap and duplicate keys?

It throws IllegalStateException: Duplicate key. Supply a merge function as the third argument, e.g. (a,b) -> a, to resolve conflicts.

Q147. How does Collectors.groupingBy return a map?

It builds a Map<K, List<T>> (HashMap by default), grouping stream elements by a classifier. A downstream collector such as counting() or summingInt and a map factory (TreeMap::new) can be supplied.

Q148. What is Collectors.partitioningBy?

It splits elements by a predicate into a Map<Boolean, List<T>> that always contains both true and false keys.

Views, Iteration and Fail-Fast Behavior

FAIL-FAST VS WEAKLY CONSISTENT

  • Fail-fast (HashMap, LinkedHashMap, TreeMap, Hashtable iterators): detect structural modification through modCount and throw ConcurrentModificationException, on a best-effort basis.
  • Weakly consistent (ConcurrentHashMap, ConcurrentSkipListMap): never throw CME; may or may not see concurrent changes.
  • Safe removal while iterating: Iterator.remove(), entrySet().removeIf(...), keySet().removeIf(...), values().removeIf(...), or map.keySet().removeAll(...).

Q151. What is a fail-fast iterator?

One that throws ConcurrentModificationException if the collection is structurally modified after the iterator was created, except through the iterator's own remove. It is a bug-detection aid, not a guarantee.

Q152. Why do you get ConcurrentModificationException while iterating a HashMap?

Because put or remove on the map changed its modCount during iteration, and the iterator compares expectedModCount on next(). Single-threaded code can trigger it too.

Q153. How do you remove entries safely while iterating a Map?

Use the iterator's remove() or removeIf on a view: map.entrySet().removeIf(e -> e.getValue() < 0). Alternatively collect keys first and remove afterwards.

Iterator<Map.Entry<String,Integer>> it = map.entrySet().iterator();
while (it.hasNext()) {
    if (it.next().getValue() < 0) it.remove();
}

Q154. Is updating a value for an existing key during iteration a structural modification?

No. Changing the value of an existing key (put on an existing key or entry.setValue) does not alter modCount in HashMap, so no CME occurs. Adding or removing keys does.

↑ Contents66

Views, Iteration and Fail-Fast Behavior · continued

Q155. Is the fail-fast behavior guaranteed?

No. It is best effort: in concurrent code the exception may not be thrown at all. Never write logic that depends on catching CME.

Q156. How do ConcurrentHashMap iterators behave while the map is modified?

They are weakly consistent: no exception, traversal continues, and elements added or removed after creation may or may not be seen.

Q157. Does entrySet() iteration create new entry objects?

In HashMap the entries are the actual internal Node objects, so no copy is made. Do not rely on them after the map is modified.

Q158. What happens if you call setValue on an entry from entrySet()?

It updates the value in the backing map. It is allowed for mutable maps and throws UnsupportedOperationException for immutable entries such as those from Map.entry or Map.of.

Q159. What is the effect of map.keySet().retainAll(otherSet)?

It removes all mappings whose key is not in otherSet, because the key set is a view. This is a neat way to filter a map in place.

Q160. Does iteration order of HashMap remain constant?

Not guaranteed. It can change after a resize or between Java versions, so use LinkedHashMap or TreeMap when order matters.

Part 5 · Modern API and Practice

Keys, equals/hashCode and Null Handling

GOOD KEY RULES

  • Prefer immutable keys with consistent equals() and hashCode(): String, Integer, Enum, UUID, records, LocalDate.
  • record types auto-generate equals/hashCode, making them ideal composite keys.
  • Arrays are poor keys (identity hashCode); use List.of(...) or Arrays.hashCode wrappers.
  • Null support: HashMap/LinkedHashMap one null key; TreeMap none (natural order); Hashtable, ConcurrentHashMap, ConcurrentSkipListMap, Map.of none.

Q161. What are the rules for a good Map key?

Immutable (or effectively immutable), with equals() and hashCode() consistent with each other and a well-distributed hash. For TreeMap, a compareTo consistent with equals.

Q162. What happens if you override equals() but not hashCode() for a HashMap key?

Equal objects may produce different hash codes, so they land in different buckets and get fails to find an entry that appears equal.

Q163. How do you use a composite key in a Map?

Create a small immutable class or a record with fields as the key, e.g. record Key(String a, int b){}, or use List.of(a,b). Avoid concatenated strings, which are error-prone.

Q164. Can you use an array as a HashMap key?

Technically yes, but arrays use identity hashCode/equals, so a different array with equal content is a different key. Use List or wrap with Arrays.hashCode/Arrays.equals.

Q165. How does HashMap handle a null key?

It treats a null key as hash 0 and places it in bucket 0. get(null) and put(null, v) work as for any other key.

↑ Contents68

Keys, equals/hashCode and Null Handling · continued

Q166. Which Map implementations reject null keys and which reject null values?

Reject null keys: TreeMap (natural order), Hashtable, ConcurrentHashMap, ConcurrentSkipListMap, EnumMap, Map.of. Reject null values: Hashtable, ConcurrentHashMap, ConcurrentSkipListMap, Map.of. HashMap and LinkedHashMap allow both.

Q167. Why is it risky to use Double or Float as map keys?

Equality of floating values depends on exact bit representation (NaN equals NaN in Double.equals, 0.0 differs from -0.0), and arithmetic rounding makes lookups unreliable. Prefer integers, BigDecimal (with care for scale) or strings.

Q168. Does HashMap use == or equals() to compare keys?

Both: it first checks == (fast path) then equals(), after confirming the stored hash matches. Hence overriding equals matters for lookups.

Q169. HashMap vs LinkedHashMap vs TreeMap: compare them.

HashMap: unordered, O(1), nulls allowed. LinkedHashMap: insertion/access order, O(1), a little more memory. TreeMap: sorted order, O(log n), no null key with natural ordering, supports navigation.

Q170. HashMap vs ConcurrentHashMap: what is the difference?

HashMap is not thread-safe and allows nulls; ConcurrentHashMap is thread-safe with fine-grained locking, forbids nulls, has weakly consistent iterators and atomic compound operations.

Q171. HashMap vs Hashtable vs Collections.synchronizedMap vs ConcurrentHashMap?

HashMap is fastest but unsafe; Hashtable and synchronizedMap give coarse single-lock safety; ConcurrentHashMap gives scalable safety. Prefer HashMap in single thread and ConcurrentHashMap in multi-thread.

Comparisons and Trade-Offs · continued

Q172. TreeMap vs ConcurrentSkipListMap?

Both are sorted NavigableMaps with O(log n) operations. TreeMap is faster single-threaded but not thread-safe; ConcurrentSkipListMap is lock-free and thread-safe with O(n) size.

Q173. HashMap vs IdentityHashMap?

HashMap compares keys with equals()/hashCode(); IdentityHashMap with == and identityHashCode, using open addressing. Use IdentityHashMap only for identity semantics.

Q174. HashMap vs WeakHashMap?

Functionally similar, but WeakHashMap holds keys weakly, so entries can vanish after GC when keys are no longer referenced elsewhere. HashMap keeps entries until removed.

Q175. HashMap vs EnumMap?

EnumMap is an array indexed by ordinal for enum keys: faster, more compact and ordered by declaration. HashMap accepts any key type and supports a null key.

Q176. Map vs Set vs List: when would you pick each?

List for ordered sequences with duplicates, Set for unique elements, Map for lookup by key. Every Set is implemented over a Map (HashSet over HashMap, TreeSet over TreeMap).

Q177. Why are HashSet, LinkedHashSet and TreeSet built on maps?

Each stores elements as keys in a backing map with a dummy constant value, reusing the map's uniqueness and ordering semantics: HashSet→HashMap, LinkedHashSet→LinkedHashMap, TreeSet→NavigableMap.

Q178. Collections.unmodifiableMap vs Map.copyOf vs Map.of?

unmodifiableMap is a read-only view over a mutable map; Map.copyOf snapshots an existing map immutably; Map.of builds a small immutable map from literals. The latter two forbid nulls.

Q179. Hashtable vs Properties vs HashMap<String,String> for configuration?

Properties adds file loading/storing and defaults but inherits Hashtable's flaws. HashMap<String,String> is cleaner in memory, and frameworks (Spring Environment, typesafe config) are preferred in real apps.

Q180. Which Map has the best iteration performance?

LinkedHashMap iterates in O(size). HashMap iterates in O(capacity + size), so large sparse tables are slower. TreeMap iterates in O(n) in key order; EnumMap iterates over a small array.

Q181. Compare memory overhead of HashMap, TreeMap and EnumMap.

HashMap uses a Node (hash, key, value, next) per entry plus the table; TreeMap's Entry adds left, right, parent and colour; EnumMap only stores a values array and is the leanest.

Q182. ConcurrentHashMap vs synchronized (map) blocks: which to choose?

ConcurrentHashMap, unless you need to lock multiple operations as one unit across the map. Its atomic methods cover most compound-action needs without blocking readers.

Q183. Which map is best for read-heavy, rarely-updated shared data?

ConcurrentHashMap, or an immutable map swapped through a volatile reference (copy-on-write). Updating by replacing the entire immutable snapshot is lock-free for readers.

Q184. When would TreeMap beat HashMap in practice?

When you need ordered iteration, range queries (subMap), nearest-key lookups (floorKey) or deterministic ordering for output, or when keys have poor hashCodes but a good comparator.

Coding and Scenario Questions

COMMON PATTERNS

  • Counting: merge(k,1,Integer::sum). Grouping: computeIfAbsent(k, x -> new ArrayList<>()).add(v).
  • Lookup for complements: store seen values in a HashMap (Two Sum). First unique: LinkedHashMap.
  • Caches: LinkedHashMap (LRU), ConcurrentHashMap.computeIfAbsent (memoization), WeakHashMap (metadata).

Q185. How do you count word frequencies using a Map?

Iterate the words and use merge. For sorted output, use TreeMap, or sort entries by value.

Map<String,Integer> freq = new TreeMap<>();
for (String w : text.split("\\s+")) freq.merge(w.toLowerCase(), 1, Integer::sum);

Q186. How would you solve Two Sum using a HashMap?

Store each number's index as you iterate; for each value check whether target - value is already in the map. This gives O(n) time instead of O(n²).

Map<Integer,Integer> seen = new HashMap<>();
for (int i = 0; i < a.length; i++) {
    Integer j = seen.get(target - a[i]);
    if (j != null) return new int[]{j, i};
    seen.put(a[i], i);
}

Q187. How do you group anagrams using a Map?

Use the sorted characters of each word as a key and collect words into a list: groups.computeIfAbsent(key, k -> new ArrayList<>()).add(word).

Q188. How do you find the first non-repeating character in a string?

Use a LinkedHashMap<Character,Integer> to count occurrences while preserving encounter order, then return the first entry with count 1.

Coding and Scenario Questions · continued

Q189. Design a thread-safe LRU cache in Java.

Wrap a LinkedHashMap (access order, removeEldestEntry) with Collections.synchronizedMap or guard it with a lock. For production use Caffeine, which uses a concurrent segmented design.

Q190. How would you build a leaderboard that keeps scores sorted?

Use a TreeMap<Integer, List<String>> (descending comparator) or ConcurrentSkipListMap for concurrent updates, and headMap/firstEntry for top-N queries. A priority queue is an alternative for top-K only.

Q191. How do you merge two maps, summing values of common keys?

b.forEach((k,v) -> a.merge(k, v, Integer::sum)); merges b into a, adding values for common keys.

Q192. How do you sort a Map by value in descending order?

Stream entries, sort with Map.Entry.comparingByValue(Comparator.reverseOrder()), and collect into a LinkedHashMap, since HashMap and TreeMap cannot hold a value ordering.

Q193. How would you implement memoization using a Map?

Use cache.computeIfAbsent(n, this::compute), for example a Fibonacci cache. For recursion use an explicit lookup/put instead, because recursive computeIfAbsent on HashMap or ConcurrentHashMap is unsafe.

Q194. How do you find the key with the maximum value in a Map?

Collections.max(map.entrySet(), Map.Entry.comparingByValue()).getKey(), or stream with max(Map.Entry.comparingByValue()). Handle an empty map first.

Q195. How do you convert a List of objects to a Map by id?

list.stream().collect(Collectors.toMap(Item::id, Function.identity())). Add a merge function if ids may repeat, otherwise IllegalStateException is thrown.

Q196. How would you model a one-to-many relationship in a Map?

Map<K, List<V>> populated through computeIfAbsent(k, x -> new ArrayList<>()).add(v); use Set<V> for uniqueness. Guava's Multimap offers a ready-made abstraction.

Q197. How would you implement a time-based key-value store (get value at a timestamp)?

Keep a Map<String, TreeMap<Integer,String>>: the TreeMap per key stores timestamp→value, and floorEntry(ts) returns the latest value at or before the timestamp in O(log n).

Q198. How would you build a thread-safe cache that loads values only once per key?

Use ConcurrentHashMap.computeIfAbsent(key, loader), which runs the loader atomically once per key. Keep the loader short, or store Future/CompletableFuture values to avoid blocking the bin.

Q199. How would you use an EnumMap in a state machine?

Define EnumMap<State, Map<Event, State>> (or EnumMap of EnumMap) as the transition table. Lookup is O(1) array access and the structure documents the allowed transitions.

Q200. What would you answer to 'What changed in HashMap in Java 8?'

Treeified bins (red-black trees) for heavy collisions, tail-insertion that preserves order during resize, simplified hash spreading h ^ (h>>>16), and new default methods (merge, compute*, getOrDefault) on the Map interface.
